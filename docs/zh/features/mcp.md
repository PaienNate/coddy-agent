# MCP 服务器集成

## 概述

智能体支持连接外部 MCP（Model Context Protocol）服务器，这些服务器提供额外的工具和资源。MCP 服务器在两份文件中声明，ACP 客户端也可以添加自己的服务器：

1. **全局**（作用域 `global`） - 用户全局的 `~/.coddy/mcp.json`（相当于 Cursor 的 `~/.cursor/mcp.json`；位于智能体主目录中，因此如果 `CODDY_HOME` 或 `--home` 将其移动，则位于别处），一个运行中的服务器由该进程的每个会话共享（[共享服务器](#共享服务器)）
2. **本地**（作用域 `local`） - `<workspace>/.coddy/mcp.json`，对于该工作区中的会话会合并到全局列表之上，每个工作区一个运行中的服务器；同名的本地条目会覆盖全局定义
3. **按会话** - 由 ACP 客户端在 `session/new` 参数中提供

`config.yaml` 不声明任何 MCP 服务器。它只保留不绑定到单个服务器的 `mcp` 设置（`project_trust`、`idle_timeout_seconds`），而仍然带有旧 `mcp_servers` 列表的配置会在下次加载时将其移交（[从 config.yaml 迁移](#从-configyaml-迁移)）。

来自所有已连接 MCP 服务器的工具会在 ReAct 循环期间合并到传给 LLM 的工具列表中（在 **`agent`** 和 **`plan`** 模式下）。

![已配置 MCP 服务器的一生：它在哪里声明、项目声明的信任门、共享服务器池、拨号及其重试，以及什么会到达模型](../../assets/diagrams/mcp-servers.png)
*一个运行中的服务器服务于每个以相同方式解析其声明的会话，而项目声明只有在信任门允许后才会启动。*

## mcp.json（全局与本地）

两个 mcp.json 文件使用与 Cursor 相同的形状：一个以服务器名称为键的单一 `mcpServers` 对象。`env` 和 `headers` 是 JSON 对象（不是 YAML 名称/值列表），而按工具开关使用 `disabledTools`：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "${CWD}"],
      "env": { "SOME_TOKEN": "value" },
      "disabled": false,
      "disabledTools": ["write_file"]
    }
  }
}
```

损坏的 `mcp.json` 会被记录并跳过；会话仍会以其余层级启动。

### 值

一个值 - 命令、参数、环境值、URL、标头 - 会在服务器启动时解析：

- `${CWD}` 是会话的工作区；
- `${NAME}`（或 Cursor 的 `${env:NAME}`）是 Coddy 进程中的该变量，未设置时为空，而 `${NAME:-default}` 在未设置或为空时回退到 `default`，因此令牌不会留在文件中；
- `$${` 是字面量 `${`，其他每个 `$` 都是字面量（带美元符号的密码无需转义），而开头的 `~` 是用户主目录。

这些规则在两份文件中以及对于 ACP 客户端发送的服务器都是相同的。文件保留引用，而对项目声明的批准会对引用（而不是值）做摘要。由于环境值或标头值从不显示（服务器列表会在其位置显示 `<redacted>`，见[管理 API 与 UI](#管理-api-与-ui)），每个批准界面都会列出声明所读取的变量（`reads: ${AWS_SECRET_ACCESS_KEY}`），因此，如果一个检出中的服务器会发送其中一个变量，那么在批准前就能看到它会这样做。批准也会记录这些名称，而较早发布给出的批准（当时项目文件中的 `${NAME}` 保持字面量）批准了一个不读取任何内容的声明：值中指名某个变量的项目服务器会被再次询问，而对不读取任何内容的声明的批准则继续有效。

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
```

### 在 Coddy 之外所做的编辑

`coddy serve`、控制台和 `coddy acp` 会监视 `~/.coddy/mcp.json`，并在其发生变化约两秒后让活动会话保持一致，无论更改者是谁：编辑器、使用文件工具的智能体，还是另一个进程。只会协调声明或开关发生变化的服务器，就像设置中的开关一样：添加的服务器会启动，移除的会关闭，重新声明的会从新声明重新启动，而其他服务器保留其进程。工具开关不会重新连接任何内容。处于轮次中途的会话会在下一轮次开始时获得新服务器。无法读取的文件（在写入中途捕获或保存时带有拼写错误）不会停止任何内容：运行中的服务器会保留，日志会说明原因，而下一次可读取的保存会与当时正在运行的内容进行比较。对项目 `.coddy/mcp.json` 的更改会在会话启动时、切换到该工作区时，以及通过 `/mcp` 或设置保存、切换或批准服务器时到达会话。

## 从 config.yaml 迁移

较早的发布还会从 `config.yaml` 中的 `mcp_servers` 列表读取服务器。首次加载此类文件时，会将列表移入 `~/.coddy/mcp.json`，并从 `config.yaml` 中移除该键：

- 每个服务器都会以其名称写入该文件，并将 `env` 和 `headers` 转换为对象；文件已声明的名称会按文件中的原样保留；
- 每个值都保持其在 `config.yaml` 中的含义：环境引用（`${GITHUB_TOKEN}`，或裸 `$GITHUB_TOKEN`）会写成 `${GITHUB_TOKEN}`，文件会在服务器启动时解析它，因此不会写入机密；`${CODDY_HOME}` 会写出为其所指的主目录，`$$` 写成单个 `$`，而 `${CWD}` 保持不变；
- `config.yaml` 的其余部分逐字节保持不变，紧挨该键上方的注释行会随之一起处理，旧文件会保留在其旁边，命名为 `config.yaml.bak-<time>`，日志会列出已迁移的服务器以及文件原本已有的服务器。

当 `~/.coddy/mcp.json` 无法读取时，不会移动任何内容：日志会说明原因，旧列表会留在 `config.yaml` 中不再使用，直到文件被修复；从设置保存会将其原样保留在那里。该块结束于解析器放置下一个键的位置，因此条目中第 0 列的注释、未使用缩进编写的列表或在第 0 列闭合的流式列表都会整体处理。流式映射中的键（`{mcp_servers: [...], ...}` 在一行内）不是行块：其服务器会迁移，键会保留，日志会要求手动删除它。`coddy -t` 会将遗留键报告为警告，说明服务器去向，并且不写入任何内容。Web 设置的 **MCP 服务器** 选项卡保留其地址 `#/settings/mcp_servers`。

## 面向项目本地服务器的工作区信任

为回应[问题 #80](https://github.com/coddy-project/coddy-agent/issues/80)而添加：在此信任门存在之前，为检出创建或恢复会话会运行 `<workspace>/.coddy/mcp.json` 要求的任何内容，而在通往 `cmd.Start()` 的路径上没有任何信任决策。

项目文件位于仓库内部，因此编写该检出的人可以决定 Coddy 在引导会话时会启动的进程的 `command`、`args` 和 `env` - 在模型运行之前，在任何工具权限提示存在之前。因此，Coddy 默认将 `<workspace>/.coddy/mcp.json` 条目视为不受信任，并且只有在操作员为该工作区批准该确切声明后才会启动它们。

- `~/.coddy/mcp.json` 由操作员编写，**不**受信任门限制；
- 该策略是 `config.yaml` 中的 `mcp.project_trust`：`ask`（默认）、`allow`（自动启动项目服务器；仅用于你已信任的工作区）、`deny`（从不加载它们，无批准路径）。控制台、`coddy acp` 和 `coddy serve` 也接受 `--mcp-project-trust ask|allow|deny`，它仅覆盖该进程的配置 - 该标志是 CI 任务或容器入口点使用的，而不是编辑 config.yaml。未知值会导致启动失败，而不是回退到默认值。该标志在进程的整个生命周期内有效：从设置屏幕、MCP 选项卡或 `config_commit` 保存的策略会写入 config.yaml，而进程会保持该标志的策略，直到在不带该标志的情况下启动。更改后的策略也会到达活动会话：移动到 `deny` 时，它会从持有项目服务器的会话中取走这些服务器，而这些服务器会停止；
- 批准记录位于 `~/.coddy/mcp-trust.json` 中，以规范工作区路径为键（链接的 git worktree 使用其主检出的路径：[Git worktree](worktrees.md#worktree-与其主检出共享的内容)），并以承载命令的声明（transport、command、args、env、url、headers）的 SHA-256 摘要为键。每条记录都是一份收据，列出被批准的内容 - 环境变量和标头的**名称**及其值所读取的变量，绝不是它们的值；
- 重写已批准的条目会更改摘要并撤回批准，因此下一个会话会再次询问。启用/禁用和 `disabledTools` 不会：它们是操作开关，不是信任边界。摘要覆盖声明，而不覆盖其运行的文件：命令是检出中的脚本（`./tools/mcp.sh`、`node server.js`）的服务器，在该脚本更改时仍保留其批准，因此请像阅读声明一样阅读此类脚本（项目钩子文件会绑定其脚本，[钩子](hooks.md#项目文件与信任)）；
- 在生成进程或联系 URL 之前会立即重新检查信任门，无论是在会话路径还是管理探测上，因此列出服务器从不会启动未获批准的命令；
- 每个批准界面都会**首先打印有效声明**：transport、带参数的命令（或 URL）、其携带的环境变量和标头的**名称**、其值所读取的 Coddy 进程变量（`${NAME}`、[值](#值)）、进程将启动所在的工作区，以及读取该声明的文件。环境变量和标头的值从不打印，也从不存储在收据中 - 决策关注的是哪些变量到达子进程，而不是其中包含什么。这刻意多于同类智能体仅名称的提示：你无法阅读的批准不算批准。

未获批准的服务器会被跳过，并给出警告，指明服务器、工作区、摘要以及批准它的命令；会话本身会以其余服务器正常启动。

在你使用的任一界面上批准它：

```bash
coddy mcp list
```

```bash
coddy mcp trust <name>
```

`coddy mcp list` 会打印每个合并后的服务器及其作用域、信任状态和它将运行的命令；`coddy mcp trust <name>` 会再次显示相同细节，然后记录批准。`coddy mcp untrust <name>` 会撤回批准。两者都接受 `--cwd DIR`，以对当前目录以外的工作区执行操作。通过 HTTP，相同的决策是 **`POST /coddy/mcp/{name}/trust`** 和 **`POST /coddy/mcp/{name}/untrust`**，而捆绑的 UI 会在 **设置 -> MCP 服务器** 下显示一个盾牌按钮以及声明。策略本身在同一选项卡中编辑（**`POST /coddy/mcp/project-trust`**），紧邻它所管辖的服务器。通过管理 API 或 UI 编辑器添加的服务器会因写入操作本身而获得批准 - 操作员自己输入了命令。

在 `allow` 和 `deny` 下，已经没有需要按服务器决定的内容，因此按服务器的批准控件会从 UI 中完全消失：`allow` 无论如何都会启动每个项目服务器，而 `deny` 不会启动其中任何一个。盾牌仅在 `ask` 下提供。

在工作区内找到的子智能体定义（`.agents/agents`、`.coddy/agents`）遵循相同模型，但使用**同级存储**：策略 `subagents.project_trust`（`ask` / `allow` / `deny`），收据位于 `~/.coddy/subagents-trust.json` 中，以相同的规范工作区路径加上定义名称和文件摘要为键，通过 `coddy agents trust <name>` 或 `POST /coddy/subagents/{name}/trust` 批准。这两个文件刻意分开，因此 MCP 批准永远不会被解读为智能体批准，反之亦然。可能使用 MCP 工具的子智能体不会借用父级的连接：配置的服务器会**通过此信任门**针对子级的 cwd 重新解析，完全像新会话一样，而父级由 ACP 客户端提供的服务器会像原始连接一样在不受信任门限制的情况下重新拨号。工具集不能包含 MCP 名称的子级（内置 `explore`）永远不会拨号任何内容。参见 `docs/features/subagents.md`。

在工作区内找到的钩子定义文件（`.coddy/hooks.json`、Claude Code 的 `.claude/settings.json` 和 `.claude/settings.local.json`）是第三种会执行代码的项目本地内容，它们遵循相同模型，但使用第三个同级存储：策略 `hooks.project_trust`（`ask` / `allow` / `deny`），收据位于 `~/.coddy/hooks-trust.json` 中，以规范工作区路径加上工作区相对文件路径和文件摘要为键，通过 `coddy hooks trust <file>` 或 `POST /coddy/hooks/trust` 批准。在 `ask` 下，被保留的文件会被解析并列出，但其中的钩子都不会运行，会话会记录一条通知，指明批准命令。参见 `docs/features/hooks.md`。

## 启用/禁用开关

两份文件都支持在不移除定义的情况下关闭整个服务器或单个工具：

- `~/.coddy/mcp.json` 和 `./.coddy/mcp.json`：直接编辑声明时，每个条目使用 `"disabled": true` 和 `"disabledTools": ["tool_a"]`
- 对于项目条目，通过 `/mcp` 或设置所做的开关会存储在 `<home>/mcp-overrides.json` 中，以工作区和服务器为键（链接的 git worktree 共享其主检出的）。检出的 `.coddy/mcp.json` 保持不变；这些开关会覆盖其默认值。通过 API 或 UI 删除项目服务器时，声明消失后其开关也会被丢弃，因此之后同名的服务器会从其自己的声明启动，而删除失败会使服务器保持原来的开关状态。从链接的 git worktree 的文件中删除它会保留这些开关，因为它们属于整个项目。当文件无法读取时，每个项目服务器都保持关闭，而全局服务器保持自己的开关；`/mcp` 和设置会指明文件和解析错误，而不是列出服务器，直到文件被修复。此文件和 `mcp-trust.json` 会在主目录的每个进程都会获取的锁下写入，因此控制台和 `coddy serve` 在同一时刻切换或批准时不会互相覆盖。

禁用的服务器不会为新会话连接。禁用的工具（以及已禁用服务器的所有工具）会从 LLM 的工具列表中隐藏，并在分发时被拒绝。开关会在每个智能体轮次重新读取，因此切换它们（通过编辑文件或通过下方的 HTTP API / Web 界面）也会在**已在运行**的会话的下一轮次生效。

通过 `/mcp`、设置或 HTTP API 所做的开关也会立即到达活动会话，一次一个服务器：打开服务器会在信任门允许它的每个活动会话中连接它，关闭它会在那里关闭它，而其他服务器保留其进程，因此浏览器自动化服务器会保持其页面打开。关闭的全局服务器会为整个进程停止，而重新打开后，它会在任何会话请求它之前再次启动。工具开关不会重新连接任何内容。处于轮次中途的会话会为该轮次保留其工具：关闭或不再受信任的服务器会在轮次结束时关闭，而打开的服务器会在会话的下一轮次开始时启动。通过 API 或设置保存或删除服务器也会以相同方式到达活动会话，而声明已被编辑的服务器会从新声明重新启动。未在 30 秒内应答握手的服务器不会阻塞任何内容：它会被排除，而会话的下一轮次会再次尝试它。

## 管理 API 与 UI

HTTP 网关（构建标签 `http`）会在 **`/coddy/mcp*`** 下暴露合并后的服务器列表（带有探测到的工具清单）和开关端点（见 `docs/reference/http-api.md`），而捆绑的 Web 界面会在 **设置 -> MCP 服务器** 下显示它们：每个服务器的状态点、`global` / `local` 作用域徽章、可展开的工具列表及按工具开关，以及用于 mcp.json 条目的 Cursor 风格 JSON 编辑器，带有作用域选择器（全局写入 `~/.coddy/mcp.json`，本地写入 `./.coddy/mcp.json`）。全局开关会持久化到其定义文件中；项目开关会持久化在操作员的主目录中。

该列表会列出每个声明的环境变量和标头，但从不返回它们的值：每一个都会读取 `<redacted>`，无论它由哪个文件声明，而 `reads` 会列出这些值所取自的 Coddy 进程变量。命令、其参数和 URL 会按书写原样列出，因为它们正是批准所针对的内容，因此机密应放在 `env` 或 `headers` 中，或者更好的做法是放在环境中的 `${NAME}` 中。探测错误在列出之前也会以相同方式清理：URL 按书写原样出现，包括 `${NAME}` 引用，而声明解析出的值（环境值或标头值、其读取的变量、八个字符或更长）会读取 `<redacted>`，即使服务器将其回显也一样。控制台和 Telegram 的 `/mcp` 会显示相同的已清理错误。

编辑器会从所列条目开始，包括占位符。保留为 `<redacted>` 的值会保持文件所存储的内容，新值会替换它，而从 JSON 中删除的键会从条目中删除；对于文件未存储值的键，占位符会被拒绝，因为该值必须输入。保存会通过其 `fingerprint`（`PUT /coddy/mcp/{name}?fingerprint=`）指明编辑器打开的声明：如果此时文件中保存的是另一个声明，则保存会被拒绝（`409`），并且不会写入或批准任何内容，因此请重新打开该条目。项目条目只有在具有该指纹时才会保留隐藏值，这样，检出在列出之后放入文件中的值就永远不会被写回并在未看见的情况下获得批准。

如果加载或刷新列表失败，设置会显示错误，并让先前加载的任何服务器保持可见。刷新仍可用于再次尝试。失败的开关、信任决策、删除或保存会报告错误并释放其控件，以便操作员无需重新打开设置即可重试。重叠的加载会按顺序应用：较慢的进行中请求永远不会覆盖或报告在较新请求已经带来的行之上。

在 Web 输入框中输入 `/mcp` 以打开此设置章节；命令后的文字会被忽略，就像在控制台中一样。在控制台中，`/mcp` 会打开一个全局和项目服务器列表，其中包含连接状态和工具计数，而 `off` 会出现在已关闭且状态为信任判定的服务器旁边。Enter 会打开服务器的控件：切换服务器、展开其工具并切换其中一个，或为项目声明授予或撤销信任。信任控件遵循 Web 盾牌的规则，并且仅在 `mcp.project_trust: ask` 下提供，因为在 `allow` 和 `deny` 下没有需要按服务器做出的决策。在记录信任之前，控制台会在选择项上方打印整个声明：transport、命令行或 URL、其变量和标头的名称、工作区以及文件。这些控件也可在 `--remote` 模式下通过服务器的 MCP 管理路由工作。Telegram `/mcp` 会列出服务器，并且仅对已受信任的条目提供启用/禁用按钮；在群组中，它需要提及机器人（`/mcp@botname`），而点按失败会在菜单消息中报告。请在控制台、CLI 或 Web 界面中批准项目声明；聊天无法授予工作区信任。

来自控制台、Web 盾牌或远程控制台的批准会通过列表所报告的 `fingerprint` 指明向它展示的声明。当检出在列出与批准之间重写了条目时，批准会被拒绝（通过 HTTP 时为 `409`），并且不会记录任何内容：请重新列出服务器并审查新声明。

*Web `/mcp` 命令会打开服务器控件，包括项目信任和按服务器开关。*

## 对话记录中的 MCP 调用

Web 界面会将 MCP 调用命名为其服务器上的操作（*在 MCP 服务器 github 上调用 get_issue*），并以卡片而不是 JSON 的形式打开它：栏中会列出服务器和工具，参数是字段，而答案按其形状读取 - JSON 对象作为相同字段，其他 JSON 缩进显示，Markdown（标题、代码围栏、列表）作为文档，其他任何内容作为等宽文本。数字和 JSON 会按服务器写入的原样显示，因此超过 2^53 的 id（Discord 或 Twitter 雪花 ID）不会被舍入，重复键会保留两个值。失败的调用会将其错误保留为原始文本。`tools/call` 结果的 `text` 块会到达对话记录和模型。`image` 块 - 浏览器服务器的截图、图表 - 会与调用一起保留，在其卡片下方预览，并展示给可读取图像的模型，检查方式与 `read` 检查图像文件相同（[MCP 工具返回的图片](images.md#mcp-工具返回的图片)）。有关卡片和截图，请参见 [Web 界面](../surfaces/web-ui.md)。

结果可能携带的其他块也会到达智能体。嵌入资源的文本会在结果中替代它，位于一行指明其 URI 和类型的内容之下，`[MCP resource 1: file:///srv/notes.md (text/markdown)]`，而资源链接会作为一行出现，包含其地址、标题、类型和大小，其描述位于下方。图像类型的二进制资源就像图像块一样是图片。任何其他二进制资源和音频剪辑都会作为文件保存在会话的 `assets/` 目录中，每个文件都带有其类型的扩展名，结果会列出每个文件的 URI、类型、大小和路径，以便智能体可以用其工具打开它；不会向任何模型发送它们：

```text
[MCP audio 1: audio/wav, 120344 bytes, saved as /home/me/.coddy/sessions/sess_4d2c9a1e7b3f5a60/assets/browser-record-audio-1-9c2f4e1a0b7d3e58.wav]
```

一次调用最多保留 20 个文件，其图片和文件合计最多占用 20 MB；超过此限制的内容，以及数据不是 base64 的块，会在结果中改为列出名称。服务器标记为错误的结果会保留其文本（包括其资源的文本），而不保留任何二进制内容。

## 支持的传输

### stdio（支持）

MCP 服务器作为子进程运行。通过 stdin/stdout 通信（换行分隔的 JSON-RPC 2.0）。该子进程会获得自己的进程组，因此停止服务器也会停止它启动的内容（[共享服务器](#共享服务器)）。

Coddy 会完全按书写原样使用 `args` 运行 `command`：按路径或按其在 `PATH` 上的名称指定的程序，诸如 `npx -y <package>` 或 `uvx <package>` 之类的包运行器，使用 `docker run -i` 启动的容器。命令所需的内容由操作员提供 - `npx` 需要 Node.js，尚未在其缓存中的包需要网络 - 而 Coddy 既不会重写参数，也不会安装任何内容。程序、`npx` 包、Streamable HTTP 服务器和 SSE 服务器都会由 `features/mcp_tool_calls.feature` 通过真实轮次运行，并在控制台中由 `examples/cli/cli_e2e_mcp_servers.py` 运行。

在 `session/new` 中的配置：
```json
{
  "name": "my-server",
  "command": "/path/to/mcp-server",
  "args": ["--stdio"],
  "env": [
    { "name": "API_KEY", "value": "secret" }
  ]
}
```

在 `~/.coddy/mcp.json` 中：
```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/projects"]
    }
  }
}
```

### Streamable HTTP（支持）

`type: http` 会通过 MCP Streamable HTTP 传输（2025-03-26 规范）连接到 `url`：JSON-RPC 消息会 POST 到端点，并以 `application/json` 主体或 `text/event-stream` 块的形式应答；初始化时发放的 `Mcp-Session-Id` 会在后续请求中回显。`headers` 会随每个请求发送（例如 `Authorization`）。仅 URL 的条目（无 `command`、无 `type`）默认为 `http`。当端点拒绝握手时（旧版服务器以 4xx 应答 POST），客户端会自动回退到同一 URL 上的旧版 SSE 传输，与 Cursor 和 Claude Code 的行为一致。事件流上的消息 - 无论是此传输还是旧版传输 - 一行最多可占用 32 MB，足以容纳以 base64 携带 20 MB 图片的结果。Coddy 不会恢复流，因此如果调用的事件流在其答案之前关闭或中断，它会立即失败，而不是等待轮次被取消。智能体会通告 `mcpCapabilities.http: true` 和 `mcpCapabilities.sse: true`。`type` 值是 `stdio`、`http` 或 `sse`，并且也接受 `http` 的 `streamable-http` / `streamable_http` 别名。

```json
{
  "mcpServers": {
    "remote-tools": {
      "type": "http",
      "url": "https://mcp.example.com/mcp",
      "headers": { "Authorization": "Bearer ${MCP_TOKEN}" }
    }
  }
}
```

### SSE（支持，旧版）

`type: sse` 会强制使用 2024-11-05 HTTP+SSE 传输：`url` 上的 GET 流会在其第一个事件中通告 POST 端点，然后承载每个服务器到客户端的消息。对于仅实现较旧协议的服务器，请使用它；`type: http` 也会通过自动回退到达它们。

在 `.coddy/mcp.json` 中，相同的条目看起来像 Cursor 的：

```json
{
  "mcpServers": {
    "remote-tools": { "url": "https://mcp.example.com/mcp" },
    "legacy-tools": { "type": "sse", "url": "https://old.example.com/sse" }
  }
}
```

## 工具命名空间

为避免多个 MCP 服务器提供同名工具时发生冲突，工具会使用服务器名称进行命名空间划分：

- 提供工具 `read_file` 的 MCP 服务器 `filesystem` -> 可用作 `filesystem__read_file`
- 内置工具 `read_file` -> 可用作 `read_file`

由于 `__` 分隔服务器部分和工具部分，服务器名称不得包含 `__`（管理 API 会拒绝此类名称）。

## 工具如何到达模型

MCP 工具**不会**注入到系统提示词文本中（不同于技能，技能会渲染到提示词章节中）。它们会加入每个 LLM 请求的原生函数调用 `tools` 数组中的内置工具，每个启用的工具一个定义：名称为 `server__tool`，服务器的自有 `inputSchema`，以及带有前缀 `[server]` 的描述，以便模型区分提供商。当模型发出名称包含 `__` 的工具调用时，智能体会通过其传输将调用路由到所属服务器，并将 MCP 结果作为常规工具观察返回给模型 - 与内置工具相同的循环，也是 Claude Code、Codex 和 Cursor 使用的方法。端到端正常路径（两个服务器分别通过 stdio 和 Streamable HTTP，模型按其命名空间工具选择一个，结果落在最终答案中）在 `features/mcp_tool_calls.feature` 中为 OpenAI 兼容 HTTP 界面和 ACP 会话流程分别规定。

## 权限模型

服务器是否**可以启动**由上述工作区信任门决定。运行中的服务器**可以做什么**不会提示：MCP 工具调用会在没有内置权限提示的情况下分发，这些内置权限提示用于保护文件系统写入和 shell 命令，而禁用开关是限制它们的机制。建议使用最小权限凭据运行 MCP 服务器，并禁用你不需要的工具。

## 共享服务器

配置的服务器会为使用它的会话运行一次，而不是每个会话运行一次。每个会话，以及会话生成的每个子智能体，都会持有对进程所共享连接的租约：

- `~/.coddy/mcp.json` 的服务器对于整个 Coddy 进程是一个进程。`coddy serve`, the console and `coddy acp` 会在它们启动时、任何会话请求它们之前启动这些服务器，并让它们保持运行直到退出：打开的会话会发现它们已连接，而关闭的会话不会停止它们。该集合会跟随文件变化：添加或打开的服务器会立即启动，移除或关闭的服务器会在没有会话持有它时立即停止，而崩溃的服务器会由下一个需要它的会话或轮次重新启动。一次性的 `coddy -p` 会为其会话启动它们，并在退出时停止它们。
- 项目的 `.coddy/mcp.json` 中的服务器每个工作区一个进程，而链接的 git worktree 会共享其主检出的那一个，除非声明中指名 `${CWD}`，它会解析为每个检出的文件夹（[Git worktree](worktrees.md#worktree-与其主检出共享的内容)）。工作区中第一个需要它的会话会在信任门允许后启动它，而该工作区的其他会话会共享它。当该工作区不再有任何会话持有它时，它会继续运行 `mcp.idle_timeout_seconds`（默认 300，即五分钟；`0` 会立即停止它），因此在此期间在该项目中打开的会话（控制台中的 `/new`、聊天中的新对话、计划任务的下一次运行、在浏览器中重新打开的同一项目）会发现它正在运行，然后它会被停止。声明相同命令的两个工作区会各自获得一个进程，除非它们是主检出及其 worktree。
- 其 `command`、`args`、`env`、`url` 或 `headers` 包含 `${CWD}` 的全局服务器会在每个工作区中解析为不同结果，因此它也像项目服务器一样每个工作区运行一次，并且不会在会话之前启动。

空闲超时针对的是配置仍然需要、但没有会话恰好持有的服务器。关闭的服务器、批准被撤回的服务器、从其文件中移除的服务器以及现在声明不同的服务器，会在没有会话持有时立即停止，包括已经在等待超时的服务器。超时在 `config.yaml` 中设置（Web 设置没有对应字段，并会在保存时保留它）：

```yaml
mcp:
  project_trust: ask
  # seconds an MCP server no session holds keeps running; 0 stops it at once
  idle_timeout_seconds: 300
```

当声明对会话解析为相同内容时，会话会共享连接：stdio 服务器的名称、传输、命令行和环境（或远程服务器的 URL 和标头），以及对于绑定到工作区的服务器而言的工作区。关闭的工具不会拆分任何内容，因为每个会话都会过滤自己的工具列表。文件编辑或开关会按下文所述协调活动会话，而声明未更改的服务器会在整个过程中保留其进程；命令行被编辑的服务器会从新声明启动一次，而旧进程会在最后一个会话释放它时停止。

停止 stdio 服务器意味着关闭其 stdin（MCP 要求客户端执行的关闭操作），给它两秒钟退出，然后终止其进程组：包运行器（`npx -y <package>`、`uvx <package>`）会将实际服务器作为自己的子进程启动，而该子进程也会随之结束。在 Windows 上，服务器运行在作业对象中，关闭该对象会结束树中的每个进程，因此父进程已经退出的子进程也会随之结束。远程服务器会被断开连接：其 SSE 流会关闭，而 Streamable HTTP 会话会通过携带其 `Mcp-Session-Id` 的 `DELETE` 结束。仍在等待答案的调用会在其服务器停止时立即失败。

自行退出的共享服务器、断开连接的远程服务器，以及为其会话应答 `404` 的 Streamable HTTP 服务器（它重启了，或使会话过期），会在使用它们的会话的下一个轮次开始时重新启动，并为所有这些会话启动一次。列出服务器（`/mcp`、设置 → MCP 服务器、聊天的 `/mcp`）会从运行中服务器的连接读取其工具，并且不会启动第二份副本。ACP 客户端通过 `session/new` 发送的服务器也以相同方式共享：发送相同声明的会话（包括继承父级服务器的子智能体）会持有一个进程，该进程会在其中最后一个关闭后 `mcp.idle_timeout_seconds` 停止。没有信任门对它们做出决定，也没有任何东西会在会话之前让它们保持运行。

`coddy serve` 会记录 `MCP server started` 和 `MCP server stopped`，以及它启动和停止的每个服务器进程的原因，因此其日志会显示有多少个正在运行以及每个为何消失。

## MCP 服务器生命周期

### 选定的 Web 会话

MCP 设置选项卡会从所选会话的工作区解析项目本地声明，而不是从启动 `coddy serve` 的目录解析。带有选定会话的请求会使用该会话的工作区；没有会话的请求会为新聊天保留服务器默认工作区。项目本地开关、信任决策和编辑只会刷新该工作区中的会话，而全局声明仍会刷新每个受影响的会话。

在捆绑的 Web 界面中打开聊天会在后台显式启动其延迟的已配置 MCP 服务器。这不会延迟对话记录的渲染，而下一个提示词会在接收其工具列表之前等待有界连接尝试。被动读取，包括斜杠补全、MCP 设置列表和分页对话记录读取，从不会启动延迟的服务器。

1. 在 `session/new` 上，会话会从合并后的 `~/.coddy/mcp.json` + `./.coddy/mcp.json` 列表中取得工作区信任门允许的每个已启用服务器，然后连接任何 ACP 客户端提供的服务器。另一个会话已在运行的已配置服务器会被共享，而不会再次启动（[共享服务器](#共享服务器)）。这些服务器会**并发**拨号，每个都有各自的 20 秒上限 - ACP 客户端发送的服务器也是如此，它们不会获得第二次尝试，因为只有该客户端才能再次声明它们（新会话可以）：该调用耗时取决于最慢的服务器，而不是它们之和；启动后从不应答 `initialize` 的服务器 - 无论是 stdio 命令，还是接受连接但保持沉默的远程 URL - 会单独失败并给出警告，而其他服务器会在其旁边连接。从磁盘恢复的会话 - 由编辑器使用 `session/load` 重新打开，或由 Web 界面或聊天读取 - 会改为在第一轮次之前通过同一信任门连接其已配置服务器：读取存储的对话不会启动进程，而以前会为每个会话启动一组并持续到服务器生命周期结束。其 ACP 客户端提供的服务器仍会在加载时连接。交互式控制台更进一步，会在**其第一帧之后**连接它打开的会话（新的或恢复的）的服务器（[控制台](../surfaces/console.md)）：`coddy` 会立即绘制，页脚会在服务器启动时对其进行计数，而在它们应答之前发送的提示词会在状态行上等待其工具列表（`Connecting MCP servers`). `coddy serve` 对其创建的会话 - Web 聊天的第一条消息、信使聊天 - 也是如此，并且仅对这些会话如此：会话会立即存在，其第一轮次会在等待服务器之前表明它已被接收（`preparing` 阶段中的 `turn_progress`），因此冷服务器不再会在线上没有任何字节的情况下阻止聊天的第一条消息。它加载的存储会话仍只会在其第一轮次启动服务器
2. 智能体会在每个服务器上调用 `tools/list` 并注册工具
3. 会话运行期间对 `~/.coddy/mcp.json` 的编辑 - 在编辑器中、在设置中、由智能体使用其文件工具进行 - 会按[在 Coddy 之外所做的编辑](#在-coddy-之外所做的编辑)所述到达它们：声明或开关发生变化的每个服务器都会自行协调，空闲会话立即协调，处于轮次中途的会话会在下一轮次开始时协调。ACP 客户端提供的服务器不会被触碰
4. 更改后的 `mcp.project_trust`（设置保存、`config_commit`、MCP 选项卡的策略选择器）会为每个活动会话重新连接已配置的服务器；ACP 客户端提供的按会话服务器保持连接。重新连接是**全新的信任评估**，而不是重放会话启动时的内容：未获批准的项目声明会保持冷状态，而在此期间批准被撤回的声明不会恢复。具有**进行中轮次**的会话不会在轮次中途被替换 - 该轮次已经将工具列表交给了模型，因此重新加载会被暂存，并在轮次释放其锁的那一刻应用。所有会话在每次保存时共享一个截止时间，而被其提前截断的拨号会被丢弃而不是安装：在首先重新连接的会话中挂起的服务器不得剥夺其他服务器的工具。这些会话会保留它们现有的服务器，并在下一轮次重试
5. 切换会话工作区（`POST /coddy/sessions/{id}/workspace` - 文件夹选择、worktree 跳转或就地分支检出）会通过相同的待处理 + 轮次锁路径为新 cwd 重新拨号已配置的服务器：新工作区的 `.coddy/mcp.json` 会被合并并重新接受信任门检查（在那里，项目声明在 `mcp.project_trust: ask` 下会保持冷状态，直到获得批准），先前工作区的已配置客户端会关闭，而 ACP 客户端提供的服务器保持连接。当对话有消息或轮次正在进行时，端点会应答 `409`，而拨号失败会发出警告并继续，而不是使切换失败。重新连接超时的切换会在会话的下一轮次开始时、在该轮次获得其工具之前完成，因此它永远不会在上一文件夹的项目服务器上运行
6. 在 ReAct 循环期间，当 LLM 调用 MCP 工具时，智能体会转发该调用（除非该工具或其服务器此后已被禁用）
7. 结果会作为工具观察返回给 LLM
8. 当会话关闭时，它会归还其服务器：项目服务器和 ACP 客户端提供的服务器会在最后一个持有它的会话释放后 `mcp.idle_timeout_seconds` 停止，而全局服务器会随进程保持运行

捆绑的 `/configure-coddy` 技能会告诉智能体当用户要求安装服务器时如何安装：验证包及其所需内容，解释它将运行什么，并且只有在用户同意后才使用其文件工具将该条目添加到 `~/.coddy/mcp.json`，同时告诉用户工具会在下一轮次到达。

## 错误处理

- 如果 MCP 服务器启动失败，会话仍会在有警告的情况下继续，并且不会在每个轮次再次拨号该服务器：对其声明的编辑、其开关（`/mcp`、设置 → MCP 服务器）、更改后的信任策略或新会话会再次尝试它
- 启动后从不应答 `initialize` 的服务器会在 20 秒后被放弃，警告会指明该上限。它会在会话的下一轮次开始时再尝试一次，因为首次启动可能因正当原因超过该上限：`npx -y <package>` 会在运行包之前安装它（在 npm 缓存为空的笔记本电脑上，`@modelcontextprotocol/server-everything` 需要 16 秒），而下一次尝试会从缓存启动它。第二次仍不应答的服务器会保持停止，直到出现上述情况之一。从外部被提前截断的拨号 - 在一个截止时间下重新连接许多会话的保存、已结束的请求 - 也会在下一轮次重试
- 服务器自己的命令在应答之前做什么由操作员决定：诸如 `npx -y <package>` 之类的包运行器会在每次启动时向其注册表询问最新发布，并等待网络，而 `args`（`<package>@<version>`）中的版本可以让它不访问网络
- 失败的 MCP 工具调用会向 LLM 返回错误观察
- LLM 可以决定重试、使用替代工具或告知用户
