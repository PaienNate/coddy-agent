# 图像

能读取图片的模型有三种途径获得一张图片：你把它附加到提示词中，智能体用 `read` 打开工作区中的图片文件，或者智能体调用的 MCP 工具返回一张图片，例如浏览器服务器的截图、一张图表。本页介绍后两种途径，以及你在哪里看到智能体所查看的内容。在 Web 输入框中附加图片见 [Web UI](../surfaces/web-ui.md#输入框文件附件多模态)，在一轮次运行期间发送消息时的附加方式见 [消息队列](message-queue.md)；在控制台或浏览器中粘贴图片，以及先对其进行标注，见 [粘贴与标注图片](picture-markup.md)。

## 能读取图片的模型

图片只会送到被标记为可接收图片的模型，标记位于 `models` 中该模型所在的行上，即 `multimodal: true`：

```yaml
models:
  - model: "openai/gpt-5.6-terra"
    multimodal: true
```

每种提供商类型都会发送这些图片：OpenAI 兼容端点以 `image_url` 部分发送，Anthropic 以 image 块发送，Codex 后端以 `input_image` 部分发送，Devin 则随提示词一起发送。附加到提示词的 SVG 属于文本，每个提供商都按文本接收它。Anthropic、Codex 后端和 Devin 接受 PNG、JPEG、GIF 和 WebP；其他类型的图片会在消息中被注明为未发送，而不会让请求失败。OpenAI 兼容端点则会收到任意类型的图片，因为该 API 背后的本地服务器可能比 OpenAI 接受更多类型。只有当模型确实接受图片时，才这样标记它；纯文本端点会拒绝携带图片的请求。

## 读取图片文件

`read` 依据内容而非名称来识别图片：PNG、JPEG、GIF 或 WebP 文件即使没有扩展名也是图片，而名为 `shot.png` 的文本文件会按文本读取。对于能读取图片的模型，`read` 会以一行作答，说明文件名、类型、像素尺寸和字节大小，并把图片本身展示给模型：

```text
screenshots/after.png: PNG image, 1280x720, 45.2 KB. The picture is attached for you to look at.
```

像请人查看一样使用它：检查测试刚刚保存的截图，比较改动前后渲染出的页面，阅读一张示意图。在同一步中读取的多张图片会一起送达模型。

出现以下情况时，图片会被拒绝并附上原因：

- 会话的模型不读取图片 - 轮次中途切换模型也算，因为检查是在读取文件时进行的；这一原因先于其他所有原因，因此模型不会被告知如何缩小一张它本来就看不到的文件；
- 文件大于 3.75 MB，base64 编码后会变成 Anthropic 每个请求中每张图片所取的 5 MB；以磁盘上的大小为准，在加载文件之前判断；
- 某一边长超过 8000 像素；
- 文件在其图片数据结束之前就结束了 - 例如仍在写入的截图、被中断的下载：PNG 会一直检查到其 `IEND` 块，JPEG 检查到其图像结束标记，WebP 逐块检查到其图像数据，而头部声明的大小与后续内容不符的 WebP 也会被拒绝，正如 libwebp 拒绝它那样；
- 文件完整但不含图片 - 没有图像数据的 PNG、没有扫描数据的 JPEG - 或者 PNG 的某个块与其校验和不符；
- 它是动画 WebP，并非每个提供商都接受；
- 内容看起来像图片但无法解码。

如果历史记录保留了一张提供商拒绝的图片，会话之后每次请求都会失败，因此这些图片会在入口处就被拒绝。智能体可以用命令保存缩小后的副本或某一帧，再读取它。GIF 会以其第一帧作为 PNG 展示：每个提供商都接受这种形式，动画的其余部分从不被解码。任何其他二进制文件 - PDF、压缩包 - 会连同其类型和大小一起被拒绝，与之前一样。

## MCP 工具返回的图片

MCP 服务器以内容块响应调用，其中 `image` 块以 base64 携带一张图片。Coddy 会把它与调用的结果一起保存，正如它保存 `read` 的图片一样，因此返回截图的服务器（浏览器自动化服务器、绘制图表的服务器）能向模型展示它所看到的内容。图片以服务器名、工具名及其在结果中的位置命名，`<server>-<tool>-<n>` 加上其类型对应的扩展名：

```text
browser-take_screenshot-1.png (from call call_7)
```

Coddy 按 `read` 检查文件的方式来检查它。类型由内容决定，无论服务器声明了怎样的 `mimeType`，并且同样的限制适用：PNG、JPEG、GIF 或 WebP，最大 3.75 MB，每边最多 8000 像素，且内容完整。GIF 以其第一帧展示。未通过检查的图片会在结果中连同原因被注明，其数据会保存为智能体可打开的文件（例如用于保存更小的副本），而结果中的文本块会保留：

```text
[MCP image 2 omitted: a PNG image of 5.1 MB, more than the 3.8 MB one picture may take; the data is kept as /home/me/.coddy/sessions/sess_4d2c9a1e7b3f5a60/assets/browser-take_screenshot-image-2-5b0e1f3c9a7d2e64.png]
```

一次调用最多保留 20 张图片、合计 20 MB，与单个请求所能携带的一样多；超出的图片会以同样的方式在结果中注明。自身没有文本的结果会列出它保留的图片，`[MCP image 1: browser-take_screenshot-1.png]`，因此控制台或编辑器中该调用的行会说明该调用返回了什么。服务器标记为错误的结果（`isError`）就是该调用的错误：模型读取其文本，其中的图片不会去往任何地方，正如失败的 `read` 不保留任何图片。图片类型的嵌入资源与 image 块一样属于图片；结果携带的其他块会怎样，见 [MCP](mcp.md#对话记录中的-mcp-调用)。

没有 `multimodal` 的模型不会被拒绝。无论哪种情况工具都返回了图片，因此 Coddy 会把它与会话一起保留，各界面会显示它，而模型只会被告知其名称；切换到能读取图片的模型后，这张图片就会像其他图片一样发送出去。

截图与其他图片一样消耗上下文。每一步都返回截图的服务器很快会让一个请求装满 20 张；随后最旧的会一起离开，降至十张，因此大约每十张截图，请求中它们所在的位置就会变化一次，而提供商的提示词缓存在其间保持有效（见 [发送给模型的内容](#发送给模型的内容)）。当模型不需要服务器的图片时，在服务器一侧关掉它们：例如 Playwright MCP 接受 `--image-responses omit`。

## 发送给模型的内容

图片会与产生它的调用的结果保存在一起，无论是 `read` 还是 MCP 调用。对话记录不会增加额外的消息，因此重新加载、控制台中的 `/resume` 或加载该会话的编辑器都会显示当时键入的对话。

发送给提供商的内容在每次请求时都根据该对话记录构建。OpenAI 兼容的工具结果不能承载图片，而且一步的结果之间不能插入任何内容，因此一步的图片会在该步工具结果之后紧随的一条用户消息中一起发送，并按读取顺序命名。该消息每次都以相同方式重建，因此提供商的提示词缓存能继续生效。

图片与模型读取的其他内容一样消耗上下文，并且会在读取它的那一步之后的每次请求中发送出去。一个请求最多携带 20 张图片、合计 20 MB，包括附加到提示词的图片和工具结果的图片：即最新的一串图片，每新增一张图片它就会增长。当新图片会使它超出任一限制时，最旧的会一起离开，直到最多剩下 10 张图片和 10 MB，但绝不会移除添加该图片的那条消息中的图片：一步的图片会一起送达模型，只有单独一步就超过一个请求所能携带的量时，才会失去其最旧的图片。之后这一串又会重新增长。在下次发生之前，每个请求的开头都与前一个请求相同，只在末尾追加，因此提供商的提示词缓存保持有效；若让图片一张一张地离开，请求就会在每一步都发生变化。附加到提示词的文本文件不算图片，也不占用图片的位置。这样就能让包含大量截图的会话保持在提供商所能接受的范围内（Anthropic API 拒绝超过 32 MB 的请求，并且当一个请求包含超过 20 张图片时，要求每边最多 2000 像素）；被排除的图片会在其原位置注明，即在其所在步骤的注解中或在其自身的提示词中。当[结果驱逐](compaction.md#结果驱逐)折叠一个旧的 `read` 时，它的图片也会一并离开；MCP 调用的结果不会被折叠，其图片只有在新图片到来时才会离开请求。无论哪种情况，注解都会告诉模型在需要该图片时重新读取文件或重复调用。上下文估算把请求携带的每张图片计为约 1600 个 token，与实际构建请求时使用的图片一致，因此驱逐、[自动压缩](compaction.md)和上下文圆环都能看到包含截图的会话的真实开销，而没有 `multimodal` 的模型不会被计入任何图片。

切换到没有 `multimodal` 的模型的会话完全不会发送图片，包括提示词附件，并且模型会被告知各步骤和提示词附带了哪些图片；附加到提示词的文本文件仍会发送，在消息中写出。

附加到提示词的文件既不是图片也不是文本时 - PDF、压缩包、有人发给 [Telegram 机器人](../surfaces/gateway.md#用户发送的照片和文件)的文档 - 会在消息中注明，而绝不会写出：把它的字节当作文本只会填满上下文窗口。文本文件会写出其前 64 KB 以内的内容，标签会说明这是其内容的多大一部分：大于上下文窗口的消息会留在历史记录中，并让之后的每次请求都失败。会话会把它收到的每个文件与其资产一起完整保留，提示词会说明位置，因此智能体可以用其工具打开它。

Coddy 会为调用返回的每张图片保留一份副本，与会话的资产放在一起（`~/.coddy/sessions/<id>/assets/`），文件名加上其内容的摘要。`read` 的结果会注明该副本、其类型和大小；提供商所需的 base64 会在请求发出时根据该副本构建，因此对话记录和运行中会话的内存都不会持有图片的第二份副本，重新读取且未发生变化的图片只会存储一次。副本会按名称在会话自己的资产目录中查找，因此迁移过的会话目录仍保留其图片，并且只会按保存时的样子发送：已丢失的副本、被链接替换的副本，或内容与其摘要不符的副本都不会出现在请求中，模型会被告知该副本已丢失，并重新读取文件或重复调用。各界面显示的是同一份副本，因此一分钟之后被覆盖的截图仍会按模型当时看到的样子预览。

## 你在哪里看到它

![在 Web 界面中读取 screenshot.png：图片预览在该行下方，然后是回答](../../assets/read-image-preview-dark-1280.png)

*`read` 向模型展示的图片，预览在其所在行下方；点击可放大打开。*

| 界面 | 显示内容 |
|---|---|
| [Web UI](../surfaces/web-ui.md) | `read` 行或 MCP 调用卡片下方的预览卡片；点击可放大打开图片。对于在控制台或 Telegram 中启动的会话同样有效，也能通过远程服务器或中继使用。 |
| [Telegram](../surfaces/gateway.md) | 机器人在轮次运行期间把图片作为照片发送到聊天中，并以其名称作为图注；一次调用的多张图片会作为最多十张的相册发送；当 Telegram 拒绝该照片本身时，则作为文档发送。 |
| [控制台](../surfaces/console.md) | 调用的行及其文本。 |
| [编辑器](../surfaces/editors.md) | 调用及其文本。 |
