# 会话目标与监督器

会话目标会让智能体持续工作，直到第二个模型确认结果。`/goal <objective>` 会设置目标并立即开始处理它。每一轮次结束后，**监督器** 会对照目标检查该轮次实际做了什么。如果还有工作剩余，它会开启另一个轮次，并指明缺少什么。当检查通过、工作需要你介入，或预算用完时，它会停止。**看门狗** 会监视相同的轮次，检查是否停滞和循环。

监督器是第二个模型，而不是执行智能体给自己评分。它判断框架记录的证据，例如工具调用、它们的结果和更改的文件，并将执行智能体的最终消息视为声明。在目标关闭之前，一个只读的**验证器**子智能体会打开工作区并确认每项要求。

## 命令

| 命令 | 作用 |
|---|---|
| `/goal [-m\|--model <id>] [-r\|--reasoning <level>] [--then-file <path>] <objective>` | 设置目标，替换任何更早的目标，并立即围绕它开启一个轮次。目标内容限制为 4000 个字符；把更长的规格放入文件并指明该文件，通过 `@` 提及（`/goal finish @plan.md`），或在输入框中附加该文件；文件会随第一轮次一起发送，执行智能体在那里读取它。`--model` 和 `--reasoning` 选择检查此目标的模型和推理级别，类似 `/compact --model`：一个已配置的 `models[].model`（或其中恰好匹配一个模型的部分）以及该模型提供的级别（其自身用 `default`）。`-m` 和 `-r` 是简写形式。`--then-file` 指定一个文件，一旦此目标达成，该文件的文本会成为新会话的目标（见[目标链](#目标链)）。 |
| `/goal` | 显示目标：其状态及原因、已使用的继续次数、上次检查的结论，以及哪些仍未完成。Web 界面和控制台则打开各自的目标菜单。 |
| `/goal pause` | 停止自动继续并保留目标。正在处理它的轮次会完成当前步骤。 |
| `/goal resume [-m\|--model <id>] [-r\|--reasoning <level>]` | 用新的继续次数和 token 预算，使暂停、阻塞或受限的目标重新变为活动状态，并开启一个轮次。目标会保留设置时使用的检查器，除非选项指定了另一个。恢复被阻塞的目标还会接受[风险门禁](#风险门禁)发现的内容（见[确认阻塞](#确认阻塞)）。 |
| `/goal clear` | 移除目标。`stop`、`off`、`cancel`、`reset` 和 `none` 也可用。 |

这些命令可在 Web 输入框、控制台、ACP 编辑器、`POST /v1/responses`、Telegram 和 Pachca 中使用。在即时通讯应用中，只有机器人管理员可以设置、暂停、恢复或清除目标；任何获准用户都可以查看它。目标在智能体模式下推进。它会随会话保存，因此能在重启后保留，压缩会在摘要中保留朝向目标的进度。

选项放在目标内容之前；它们不计入 4000 个字符。如果目标内容的最后两个词是一个选项和一个值（`/goal ship it --model mini`），或者最后一个词是 `--model=mini`，则会被拒绝，并给出指明该选项的提示，因为否则该选项会成为目标内容的一部分。以选项名再加一个词结尾的句子，例如 `document the --model flag`，也会按同样方式解析；请改写这类目标内容的结尾。使用排版破折号写出的选项（`—model`，即智能标点把 `--model` 变成的形式）如果出现在目标内容的开头和结尾，无论后面是否带值，都会被拒绝。目标内容中其他任何位置的选项名仍作为文本。在 `resume`、`pause` 或清除词之后的选项属于该子命令：`/goal resume -m <id>` 选择检查器，`pause` 和清除词会拒绝选项，那里拼错的选项（`/goal pause --modle mini`）也会被拒绝，而不会成为新目标的目标内容。

Web 输入框会在你输入 `/goal` 时按服务器的方式计数目标内容：去掉开头的选项，去除首尾空白，按字符计。它不会发送超过 4000 个字符的目标内容，服务器拒绝的 `/goal` 会连同其附加文件回到输入框，以便你缩短后再次发送。

## 目标如何推进

1. **启动。** `/goal <objective>` 存储目标并开启一个轮次，其消息告诉执行智能体现在开始，重述目标内容，并给出规则：依据证据工作，用工具结果证明主张，不要削弱检查来通过它们，当工作需要你介入时明确说明。目标内容指定的文件，即其中通过 `@` 提及的文件，或在输入框中附加的文件，会随第一轮次一起发送，因此执行智能体在那里读取它；之后的轮次会以文本重述目标内容，文件仍可通过其路径读取。
2. **检查。** 当轮次结束时，监督器会获得目标内容、上次检查的要求列表，以及一份**证据摘要**。摘要会列出目标消息中的工具调用（见[哪些消息计入](#哪些消息计入)），包括其参数以及每个结果的开头和结尾，以及各轮次更改的文件和[风险门禁](#风险门禁)的红旗标记：更改了容器或卷的 docker 命令、更改的迁移文件、编辑过的测试、测试数据或 CI 文件，以及添加的跳过或抑制标记。执行智能体的最终消息放在最后，标记为声明。监督器用要求检查清单和结论回答：
   - `met`：每项要求都由展示的工具结果证明；
   - `not_met`：仍有工作，并给出下一步；
   - `needs_user`：执行智能体提出了只有你能回答的问题、缺少访问权限，或发现请求与测试之间存在冲突；
   - `impossible`：在此工作区无法达成目标内容。
3. **验证。** `met` 结论会交给验证器，这是一个使用只读工具（`read`、`glob`、`grep`、`print_tree`）的系统子智能体，运行在监督器的模型上。它读取每项要求背后的文件，并以相同格式回答。如果发现缺口，目标会带着验证器的列表继续。它的运行会作为 **目标验证** 出现在会话的任务面板中。如果验证器自身未能回答，则检查的结论仍然有效，原因会说明未经验证。`supervisor.verify: false` 会跳过此步骤。
4. **继续。** 对于 `not_met`，下一轮次开头会给出结论的原因、仍未完成的事项、检查清单、完整目标内容，以及目前为止使用的预算。重述目标内容可防止长时间运行漂向更简单的任务。
5. **停止。** 当检查（以及验证器）发现目标已达成时，目标变为 `complete`；当工作需要你介入时，变为 `blocked` 并带上问题。当 `max_continuations` 或 `token_budget` 用完时，它变为 `limited`。在最后一次停止之前，执行智能体会得到一个收尾轮次：不做新工作，只总结已完成的内容、仍未完成的内容和下一步。在所有这些之前，[风险门禁](#风险门禁)会在某个轮次结束后立即阻塞目标，前提是该轮次的消息包含更改容器或卷的 docker 命令，或包含更改过的迁移文件。

你在监督器工作时发送的消息会优先处理；在该轮次结束后会再次检查目标。在轮次运行期间发送的 `/goal` 命令会等待该轮次结束，无论队列模式如何，并会在任何继续之前运行。在监督器检查目标时暂停、清除或替换目标会立即生效：检查结论被丢弃，且不会开始继续。如果某个轮次用 `notify_on_finish` 让后台命令或子智能体保持运行，则该轮次的检查会推迟：报告该工作的唤醒会启动下一个受监督的轮次。不会唤醒任何对象的工作，例如目标验证器自身检查这类系统任务、用 `notify_on_finish: false` 启动的任务、没有唤醒器的进程，不会被等待。停止会结束本次运行，但不改变目标状态。你的下一条消息会再次对照目标进行检查，或者使用 `/goal pause`。

监督器启动的轮次不是你输入的消息。每个界面都会将每个轮次显示为一行，实时显示，重新加载后也显示：**目标已设置：...**、**目标继续 2/10：测试仍失败**、**目标恢复 1/2：...**、**目标已恢复：...**。Telegram 和 Pachca 会将同一行作为独立消息发布，并且上一轮次的回答会先于它发送。

## 状态

| 状态 | 含义 | 什么会改变它 |
|---|---|---|
| `active` | 每个轮次结束都会检查；未完成的工作会继续。 | `/goal <objective>`、`/goal resume` |
| `paused` | 保留，不检查也不继续。原因会说明是谁暂停了它：你、使用限制、失败的轮次、失败两次的检查。 | `/goal pause`、菜单、系统 |
| `blocked` | 工作需要你介入，或连续两个轮次结束时没有任何工具调用，或从停滞或循环中恢复的次数用尽，或[风险门禁](#风险门禁)发现更改容器或卷的 docker 命令或更改过的迁移文件。原因中包含问题，或门禁写入的那一行。 | 监督器 |
| `complete` | 检查为已达成，并在验证器能够回答时由其确认；验证器无法确认的目标会在其通知和上次检查中说明 "未验证" 及原因。 | 监督器 |
| `limited` | 继续次数或 token 预算用完。 | 监督器 |

## 风险门禁

目标可以在无人看管的情况下运行数小时，而有两类步骤会造成后续轮次无法修复的损害：替换容器或卷的命令，以及重写已提交的迁移文件。在每个目标轮次之后，监督器会对目标消息中显示的内容应用两条硬性规则。违反其中一条的轮次会立即阻塞目标，并给出指明该命令或文件的一行。

这些规则适用于会话目标：用 `/goal` 设置的、用 `PATCH /coddy/sessions/{id}/goal` 设置的，或由[目标链](#目标链)设置的。`supervisor.enable` 在未设置目标时的隐式监督永远不会被阻塞，因为它不保留可被阻塞的目标状态；其检查器仍会在红旗标记中看到 docker 标记行。

### 哪些消息计入

目标的证据是目标活动期间存储的消息。每条消息都带有目标 ID，当时存储的压缩摘要和计划快照也是如此。`POST /v1/chat/completions` 的客户端在回传历史记录时会保持其重放消息的 ID 不变；它更改或添加的消息不携带任何 ID。检查器的摘要（其活动部分、文件和红旗标记）以及门禁只读取这些消息，不读取其他消息。在目标暂停、阻塞或受限期间存储的消息，例如你在此期间自行运行的轮次，不属于该目标：门禁不会读取它，摘要也不会显示它。这些 ID 永远不会发送给模型提供商。`supervisor.enable` 的隐式监督没有目标 ID，会从你的最新请求开始读取消息。

回退会连同消息携带的 ID 一起移除消息，其撤销会连同 ID 一起恢复它们。新目标有新 ID，因此更早的消息不是它的证据：即使目标内容相同，`/goal <objective>` 也会创建一个新目标；带目标内容的 `PATCH` 以及目标链的下一环也是如此。旧版 Coddy 存储的消息不携带 ID，因此在升级前设置的目标只有升级后存储的内容作为证据。

### Docker 变更

目标的 `run_command` 调用，其命令行包含词 `docker` 或 `docker-compose`，并且在同一命令中，任意位置包含 `up`、`down`、`rm`、`stop`、`restart`、`create`、`run`、`kill` 或 `prune` 之一。

门禁按词法读取命令行，而不是像 shell 那样读取。它会忽略大小写、引号字符 `'` 和 `"` 以及反斜杠（行末的反斜杠会将本行与下一行连接），在 `;`、`&`、`|` 和换行处将剩余内容切分为命令，因此涵盖 `&&`、`||` 和管道，然后查看每条命令的词。一个词是由字母、数字、`-`、`_`、`.` 和 `/` 组成的连续片段，从其最后一个 `/` 开始读取，因此路径按其最后一部分计入：`/usr/bin/docker` 就是词 `docker`。因此 `/usr/bin/docker rm x`、`>/tmp/x docker compose down`、`(docker rm x)` 和 `$(docker rm x)` 会匹配，`rm -rf docker` 和 `git rm docker` 也会匹配，其中 `docker` 表示一个文件夹。路径中间经过的文件夹本身不会成为独立的词，因此 `rm -rf docker/tmp`、`go run ./docker/gen` 和 `cat docker-compose.yml` 不匹配。`--rm` 与 `rm` 是不同的词。

这种读取方式故意做得比较粗糙。引号中的文本会像命令一样匹配（`echo "docker compose down"`、`sh -c 'docker rm x'`、here-document 正文中的一行），`--help` 和 `--dry-run` 不会豁免任何内容，`docker network create`、`docker image rm` 和 `docker compose run` 也会匹配。一次误报的代价是一次 `/goal resume`。该规则看不到的是脚本（`./deploy.sh`、`make down`）、别名、函数或运行时展开的变量（`$CMD`）所运行的内容。

从未运行的调用不计入。以下这些调用不计入：被人员拒绝的调用（`permission denied by user`、`permission not granted: ...`）、被钩子阻塞的调用（`blocked by hook: ...`）、因钩子更改了已批准的参数、因参数在权限提示前无法保存，或因轮次在钩子运行时被取消而取消的调用、在绕过模式下被[命令安全检查](decisions.md)拒绝或未运行的调用、被询问或计划模式、会话的工具集、子智能体的工具集或受限轮次（不是机器人管理员的即时通讯用户）拒绝的调用、被跳过的调用（`not executed: ...`），以及智能体的循环防护未执行的重复调用。已运行但失败的调用计入，没有记录结果的调用也计入。只有当结果携带该调用的目标 ID 时才会读取结果（见[哪些消息计入](#哪些消息计入)）。`POST /v1/chat/completions` 的客户端无法写入该 ID，因此它更改或添加的结果不会被读取。其调用会像没有记录结果的调用一样计入，摘要会显示它但没有结果。

### 迁移文件变更

目标所设置的工作区文件夹内、位于仓库任意深度、名为 `migrations/`、`alembic/versions/`、`db/migrate/` 或 `db/changelog/` 的文件夹下的受跟踪文件，且该文件在设置目标时指定的提交 `HEAD` 中已存在，并且其内容现在与该时刻的状态不同。文件夹名按从仓库根目录开始的路径匹配，因此工作区本身是此类文件夹，或位于此类文件夹之下，也会被覆盖。仅换行符不同不算变更：仅因 CRLF 与 LF 不同而与该状态不同的文件不会被报告，即使它在设置目标时已经更改也是如此。文件如何更改并不重要：`edit`、`write` 或 `apply_patch` 调用、shell 循环、`git commit`、`git checkout`、删除或重命名。索引条目被标记为 `assume-unchanged` 或 `skip-worktree`（稀疏检出的标记）的文件，`git diff` 不会查看它，但也会按内容进行比较。在目标期间新增的迁移文件不在此规则覆盖范围内。

设置目标时，它会存储起始提交、工作区文件夹，以及工作副本中已经更改的每个迁移文件的内容哈希。因此，你自己尚未提交的编辑在再次更改之前不会被归因于该目标；会话之后切换工作区也不会改变规则所比较的文件夹。

比较需要 `git` 二进制。没有内置回退方案，因此如果 `PATH` 上没有 git，该规则不可用。每次查看仓库（设置目标时、每个目标轮次结束后，以及被阻塞目标的 `/goal resume` 时）都限制在 10 秒内。当时间用完或轮次被取消时，它会在下一个文件处停止；磁盘上或提交中大于 16 MiB 的文件会使比较失败。git 配置中的 `diff.relative` 设置无关紧要。只读取 git 列为已更改的文件、被标记为 `assume-unchanged` 或 `skip-worktree` 的文件，以及设置目标时已经更改的文件。

在任何 git 仓库之外的文件夹中设置的目标没有可比较的内容：该规则不适用于它，摘要中也没有关于它的行。当没有记录起始状态（没有 `git` 二进制、尚无提交、未及时得到回答，或目标由旧版 Coddy 设置），或比较失败、超时时，摘要会说明无法将迁移文件与目标的起始状态进行比较，给出原因，并说明它们是否更改未知，而绝不会说 "无更改"。仅不可用本身从不会导致阻塞。

### 给检查器的红旗标记

同一规则表还包含两个提示性标记：测试、测试数据或 CI 文件被更改，以及某个调用添加了跳过或抑制标记。检查器会权衡它们，它们从不会导致阻塞。

每个标记，无论是硬性还是提示性，都会列在摘要的 **红旗标记** 部分，并引用相应命令或文件。即使引发该标记的步骤因大小预算而从活动部分中删除，列表仍会保留；该预算会将最新步骤控制在大约 24,000 字节以内。你已接受的发现项会以 `(acknowledged with /goal resume)` 列出。

### 门禁做什么

门禁在每个目标轮次之后运行，紧接在监督器确认该目标仍是该轮次所处理的目标且仍处于活动状态之后，并先于其他一切运行：预算用完后的收尾轮次、因排队消息而结束的轮次、失败或卡住轮次后的恢复、因后台工作而推迟的检查，以及检查本身。`/goal resume` 尚未接受的硬性发现项会立即阻塞目标，并用一行指明命令或文件：

```text
Goal blocked: run_command changed docker containers or volumes: `docker compose up -d`
Goal blocked: migration files that existed when the goal started were changed: migrations/0007_users.py, migrations/0008_orders.py
```

该行按每种发现项包含一个子句，并用 `; ` 连接。每个子句用反引号引用每条命令，用 `, ` 连接多个命令，最多列出 20 项，然后以 `and N more` 结束。门禁不请求检查，不消耗恢复轮次，不向历史记录添加消息，验证器也不会运行。在门禁读取 git 时发生的暂停、清除或替换目标会优先生效，随后门禁不再处理该目标。排在该轮次之后的消息仍会作为普通轮次在其后运行，因为目标已不再活动；在 `supervisor.enable` 下，它们会得到其隐式检查。

服务器重启后通过权限回答结束的轮次（`POST /coddy/sessions/{id}/permission` 会在监督器循环之外恢复它）在结束时也会经过同一门禁，并遵循相同的归属和取消规则。只有门禁：该轮次之后不会进行检查、恢复或继续。

门禁查看的是已经发生的事情。它从不在步骤运行之前阻止它，因此当目标被阻塞时，容器已经不存在了。要在这种步骤运行之前阻止它，请使用带 `failClosed: true` 的 `PreToolUse` 钩子；[钩子](hooks.md#示例)中有针对这两类步骤的示例。

### 确认阻塞

`/goal resume` 作用于被阻塞的目标时，会在让目标重新变为活动状态的同一次更改中，接受门禁在那一刻发现的内容：目标消息中迄今为止计入的每个 docker 调用，以及每个已更改迁移文件当时的内容。调用的接受状态存储在发起该调用的助手消息上，并随对话记录保存。文件的接受状态随目标保存。重启会保留两者。

新的匹配调用会再次导致阻塞：它是一条新消息，即使它在同一秒内以相同命令和调用 ID 存储也是如此。回退会移除已接受的消息，因此重新生成的调用会再次导致阻塞，而回退的撤销会将它们恢复为已接受状态。已接受文件进一步更改为任何其他内容会再次导致阻塞；将文件恢复到其起始状态不算更改。新目标（`/goal <objective>`、带目标内容的 `PATCH`，或目标链的下一环）会从干净状态开始。

`/goal resume` 作用于暂停或受限的目标时不会接受任何内容。目标暂停时仍在运行的轮次不会经过门禁，因此在恢复后，一旦下一个目标轮次结束，门禁会报告该轮次在暂停前存储的步骤。它在暂停后存储的内容不属于该目标。

### 限制

- docker 规则只读取 `run_command` 的命令行。脚本（`./deploy.sh`、`make down`）、别名、函数或运行时展开的变量（`$CMD`）所运行的内容不会被看到。
- 重写命令的 [`PreToolUse` 钩子](hooks.md)不会被看到：门禁按模型写入的命令原样读取。
- 子智能体自己的 `run_command` 调用在其自己的对话记录中，不会被读取。迁移规则仍会看到子智能体更改的文件。
- 目标所设置的工作区文件夹之外的迁移文件不会被检查，当会话在仓库的子文件夹中工作时，这一点很重要。
- 门禁根据结果文本判断调用未运行。已经运行、但其自身输出读起来像框架的拒绝文本（`permission denied by user`、`not executed: ...` 等）的调用会被视为未运行，其中的 docker 命令不计入。
- 这些规则是词法层面的且不完整，也不是沙箱：它们是在事后指出常见写法。

## 目标链

长时间的工作常会拆分成多个包，每个包都值得使用一个新会话：上下文保持较小，这在 32k 窗口的模型上很重要，而且每个包都从干净的交接开始。`--then-file` 会将它们串成链：

```text
/goal --then-file .coddy/next-task.md Implement the sub-plan named under current in state.md.
```

路径是一个词，不带引号或空格。链式目标的执行智能体会被告知下一项任务会写入该文件，并且只有在仍有工作时才创建该文件。当监督器发现目标已达成且验证器确认后，Coddy 会：

1. 读取该文件，路径相对于工作区（绝对路径和以 `~/` 开头的路径也可以）；
2. 将其重命名为旁边的 `next-task.started-<UTC time>.md`，这样它绝不会运行两次；
3. 在同一工作区、同一模型、推理级别和权限模式下打开一个新会话，以该文件的文本作为其目标，并使用相同的检查器和相同的后续文件；
4. 立即开始处理该目标。

两个对话记录都会得到一行，指明另一个会话：已完成的记录中为 **目标链：在会话 ... 中继续**，新记录中为 **目标链：从会话 ... 继续（第 2 个链接，共 10 个）**。目标也会携带链接信息：`GET /coddy/sessions/{id}/goal` 中的 `thenFile`、`chainIndex`、`continuedFrom` 和 `continuedIn`，以及 `session_goal` 事件中的这些内容，因此跟随 `GET /coddy/events` 的脚本会看到链继续推进。链打开的会话会以其目标命名。

当以下情况发生时，链会停止，并给出一行说明原因：

- 后续文件不存在或为空，这是工作完成后链结束的方式；
- 目标以除 `complete` 之外的任何状态结束，或被暂停或清除；目标只在智能体模式下检查，因此计划或询问轮次永远不会推进链；
- 验证器无法确认已达成的结论（使用 `supervisor.verify: false` 时，仅检查就足够）；
- 链已经打开了 `supervisor.max_chain_sessions` 个会话（默认 10 个；`0` 会关闭目标链，此时 `--then-file` 会被拒绝）；
- 文件长度超过目标内容允许的长度，或不是常规文件；它会留在原处。

新会话在无人看管的情况下运行：权限提示会得到权限模式给出的答案，而该模式会询问的任何内容都会被拒绝。无人值守的链需要权限模式 `bypass`，新会话会继承该模式，并在服务器重启后保留。无论文件由谁写入都会被读取，因此请指定一个你和智能体都能控制的文件：已经包含该文件的检出会以其文本作为下一个目标开始。

目标链在 `coddy serve` 下运行：从 Web 界面、即时通讯机器人，或通过 `--remote` 附加的控制台或编辑器设置目标。本地控制台和本地 `coddy acp` 会拒绝 `--then-file`，因为那里无法运行没有人打开的会话。在 Telegram 和 Pachca 中，聊天会收到指明新会话的那一行，仅此而已，因为新会话并未绑定到该聊天；Telegram 的 `/resume <id>` 会跟随它。

`/goal resume` 会保留后续文件，目标菜单中的 **编辑** 会将其一并发送。带目标内容的 `/goal <objective>` 和 `PATCH /coddy/sessions/{id}/goal` 会替换目标，并随之丢弃后续文件及链中的位置。

## 看门狗

当目标轮次运行时，看门狗会看到该轮次发送的每次更新。

- **停滞。** 如果在 `stall_seconds` 内没有发送任何内容，该轮次会被切断并获得一个恢复轮次。计时器会把任何更新都视为活动：文本、推理和工具调用。当权限或问题提示打开、工具运行（工具自身有超时）以及后台工作运行时，它会等待。带有 `stream: false` 的模型行在回答时不会发送任何内容，因此对它来说，计时器至少会等待该行的 `timeout_ms`（再加 30 秒），如果该行未设置，则关闭计时器。
- **循环。** 每个完成的工具调用都是一个指纹，由其名称、规范参数和结果的哈希组成。当最后若干操作形成一个长度为 1、2 或 3 的循环，并且该循环已经重复 `loop_repeat` 次时，该轮次会被切断，恢复轮次会要求执行智能体总结它尝试过的内容并改变方法。长度为 2 或 3 的循环至少需要两个完整回合。中间的助手文本不会掩盖循环。结果不同的相同调用是进展：例如以不同方式失败的测试运行，或文件更改后的读取。
- **卡住和失败的轮次。** 被看门狗切断的轮次、被智能体自己的循环防护停止的轮次，或智能体拒绝继续的轮次，会先于其他一切接受检查，因为循环的执行智能体往往就是需要你介入的那种：`needs_user` 或 `impossible` 结论会带着问题阻塞目标，任何剩余工作都会得到一个恢复轮次，该轮次会指明剩余工作并要求执行智能体改变方法或询问你。短暂的提供商错误，例如 5xx、断开的流或变得静默的流，会得到一个恢复轮次，但不进行检查。使用限制会暂停目标。任何其他错误都会以该错误为原因暂停目标。

恢复次数会计入每次运行的 `max_nudges`。当它们用完时，目标会以最后的原因被阻塞。

## 配置

目标不需要配置：没有 `supervisor` 章节，或该章节为空时，会话自己的模型会检查工作，所有边界都取默认值。

```yaml
supervisor: {}
```

每个键及其默认值：

```yaml
supervisor:
  enable: false              # check ordinary turns against the latest request too
  model: ""                  # the checking model; empty uses the session's model
  verify: true               # confirm a met verdict against the workspace
  max_continuations: 10      # automatic turns per goal, then a wrap-up turn
  token_budget: 0            # uncached input + output tokens per goal; 0 = no cap
  max_chain_sessions: 10     # sessions a goal chain (--then-file) opens; 0 = chains off
  stall_seconds: 300         # 0 turns the stall timer off
  max_nudges: 2              # recovery turns after a stall, a loop or a failed turn
  loop_repeat: 3             # 0 turns loop detection off
```

检查模型首先按目标选择：`/goal --model <id> --reasoning <level>` 优先于 `supervisor.model`，后者优先于会话的模型。`model` 指定一个已配置的 `models[].model`。留空时，会话自己的模型会检查自己的工作。没有 `--reasoning` 时，检查会以检查模型的 `reasoning_default` 运行，即使用该模型的会话启动时所用的级别；当模型未配置级别时，则使用提供商自己的级别。关于模型评判者的研究表明，模型会给自己的输出更高评价，因此即使另一个家族的模型更小，也是更好的选择。检查在无工具的情况下运行，并经过与智能体自身调用相同的重试和代理。如果回答不含有效 JSON，会再询问一次；检查失败两次会暂停目标。Web 界面中的 **设置 → 会话目标** 会编辑相同的键。

![设置 → 会话目标：从已配置模型中选择的监督器模型、目标检查和看门狗](../../assets/session-supervisor/goal-settings-dark-1280.png)

*设置 → 会话目标（深色，1280 px）。*

`enable: true` 会让普通轮次接受相同检查，并以最新请求作为目标内容。不会为它们存储任何内容：`blocked` 或受限运行会以一条通知结束。无论 `enable` 说什么，目标都会被检查。

## 各界面上的目标

- **Web 界面**：输入框上方、git 变更计数左侧、以状态颜色显示的目标标记会在 `/goal` 设置目标后出现；其提示会显示状态和目标内容。它会打开目标菜单，其中包含目标内容、状态及其原因、带验证器标记的上次检查、检查清单、各项计数、检查它的模型（**检查者**）及其检查所用的推理级别（**推理**：目标自身指定的级别，否则为模型默认值），以及作为图标的 **暂停**、**恢复**、**编辑**（保留检查器）和 **清除**。单独输入 `/goal` 会打开同一菜单。输入 `/goal --` 时，会用已配置的模型补全 `--model`，并用 `--model` 指定的模型级别补全 `--reasoning`；简写 `-m` 和 `-r` 会打开同样的列表。
- **控制台**：页脚显示目标的状态和继续次数；单独输入 `/goal` 会打开目标模态框，其中包含相同详细信息（**检查者** 一行显示检查器，**推理** 一行显示其级别）和操作。在 `--remote` 下，两者都跟随服务器。
- **HTTP**：`GET`、`PATCH`（`{"status":"paused"}` 或 `{"objective":"..."}`）和 `DELETE /coddy/sessions/{id}/goal`，一轮次流式传输中的 `session_goal` 和 `goal_turn` 事件，`GET /coddy/events` 上的 `event: session_goal`，以及 `GET /coddy/sessions/{id}/messages` 中的 `goal`；见 [HTTP API](../reference/http-api.md)。
- **ACP 编辑器**：`session_goal` 和 `goal_turn` 会话更新；两者都不渲染的编辑器仍会以文本形式收到命令的答案。
