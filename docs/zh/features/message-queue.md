# 消息队列

操作者最清楚智能体接下来该做什么的时刻，往往正是它正在工作的时候：读错文件的那次工具调用、谁都没提到的那个平台、只有把计划摆到屏幕上才显露出来的那条约束。因此，在一轮**进行中**写下的消息不会被拒绝。它会以两种模式之一在会话上等待：

- **引导（Steer）**在下一个 ReAct 步骤进入正在运行的那一轮，位置在模型刚发出的工具调用与紧随其后的请求之间。修正落在工作仍在发生的时候。
- **轮次之后（After turn）**等待答案，然后开启自己的提示词。多条延迟消息按入队顺序逐条运行。

一轮进行中第一次发送时，浏览器或控制台会询问 **Enter** 应使用哪种模式，并把答案作为 `agent.queue_mode` 保存到 `config.yaml` 中；之后可在 **Settings → ReAct loop** 中修改。一轮运行期间，**Enter** 使用该模式，**Tab** 使用另一种；浏览器的发送按钮使用 Enter 模式。在智能体读取之前，消息仍然属于你：它的模式可以切换，撤回它会把其文本和图片放回草稿。

## 智能体看到的内容

一条**引导**消息在被读取的位置成为对话中的普通用户消息。对话记录中没有任何标记表明它特殊，也没有任何东西告诉模型它是排队而来的：它就是一个人在工作进行中插话，事实也正是如此。同一步骤中写下的多条引导消息会按书写顺序一起被读取。它们的 `@` 提及和 `/skill` 调用在读取时解析，与提示词完全一样，并随消息一起携带（[提及](mentions.md)）。

读取发生在一轮中的两个位置，两者都是模型能够据此行动的最早时刻：

- **步骤之间。** ReAct 循环在每次迭代开头排空引导消息，先于它为刚刚收集到的工具结果构建请求。
- **结束时。** 若引导消息是在答案已经开始生成时写下的，同一轮会读取它并继续运行，因此它由它所写入的那一轮来回答。这次读取发生在 `Stop` 钩子表态**之后**，因此每个结束一轮的答案仍会触发钩子。

一条**轮次之后**消息是一次独立运行的提示词，在答案给出后启动：一次全新的智能体运行，拥有自己的 `agent.max_turns` 预算，能看到上一个答案留在对话中的所有内容。正在观察该会话的客户端会以获知引导读取的同样方式获知它，即作为操作者消息出现在它进入对话的位置，因此实时对话记录会把它显示在针对它的答案之上。

![一条引导消息和一条带图片的轮次之后消息，各自依次得到回答](../../assets/message-queue/message-queue-after-turn-dark-1280.png)

*引导消息在该轮结束前被读取；轮次之后的那条带着它的图片，在那次答案之后启动了自己的提示词。*

## 轮次边界与 Stop

当一轮给出答案时，管理器会在一个原子步骤中查看等待中的内容：先取所有引导消息，作为同一轮再一次运行的一个批次；否则取最早的那条轮次之后消息，单独运行；否则关闭队列。在同一把锁下做决定意味着：已经结束的轮次绝不会接受消息，而片刻之前刚切换过模式的消息会按它现在的模式处理。

除非有显式的 `continue_queue` 请求，否则只有以**答案**结束的轮次才会以此方式继续。因任何其他原因停止的轮次 - 达到轮次上限、拒绝、钩子、错误 - 已经说明了原因，再次运行会把它淹没。每个已接纳轮次的续跑上限为 **20** 次运行，即一个满队列的大小；超过上限后，引导消息会被丢弃并给出警告，而轮次之后的消息继续排入队列。

**默认取消**会丢弃未读的引导消息，并**保留轮次之后消息**但不启动它们。你可以切换或移除这些保留的消息；它们会在该会话的下一次普通答案之后运行。一条延迟消息若在进入对话之前其运行就停止了，则回到队列头部。省略 `continue_queue` 或发送 `false` 的 ACP、远程控制台和 HTTP 客户端保持此行为。错误、外部取消和服务器关闭不会触发队列续跑；尚未被已接受的续跑预留的队列保持这些默认规则。

浏览器的 **Stop generation** 按钮总是随 `{"continue_queue":true}` 发送 `POST /coddy/sessions/{id}/cancel`。当有队列在等待时，对于在该进程中执行的普通 profile 提示词运行（`agent`、`plan` 或 `ask`），服务器可以接受此请求。它在接受截止点预留所有等待中的消息，不论其是 `steer` 还是 `after_turn` 模式，并且只在接受该续跑时返回 `queueContinued: true`。空队列、直接补全、已保存计划的运行、权限恢复或 supervisor 命令都会退回完全取消。这不会新增任何路由或配置键。

对于被接受的续跑，服务器会取消当前运行的子上下文，并等待该运行展开结束，包括部分助手内容持久化和工具结果。然后它按原始 FIFO 顺序把每条预留消息作为独立的用户行追加，保留重复项和保留的图片，并启动一个新的子运行来回答它们。它不会创建空的或合成的用户提示词，也不会合并这些消息。相同的接纳与轮次代际保持有效，只有一个对话记录写入者。截止点之后入队的消息在下一个循环边界遵循现有队列规则。

![Stop 之后，排队的消息作为独立的用户行出现，同一个已接纳轮次继续。](../../assets/diagrams/queue-interrupt.png)

![Stop 之后独立的排队用户消息与仍在进行的答案](../../assets/queue-stop-continued-dark-1280.png)

*Stop 之后，排队的消息作为独立的用户行出现，同一个已接纳轮次继续。*

若第一批预留尚未被读取时再次按下 Stop，则以完全取消优先。服务器会保留那批未读的已接受批次而不是丢失它，但不会自动启动它。外部取消、错误和关闭也不会自动恢复它。续跑确认并不证明其答案已经完成。队列保留在进程内存中，不会在进程重启后存活。

其他提示词路径在支持的情况下仍会在自己的步骤之间读取引导消息；若没有已接受的续跑，它们在结束时丢弃未读的引导消息并给出警告，同时让轮次之后消息继续排队。

### 智能体自己运行的一轮

由本地智能体（`providers[].type: acp`、[作为模型的 ACP 智能体](acp-provider.md)）服务的一轮是一次可能持续数分钟的调用，Coddy 在其中没有 ReAct 步骤。它的步骤边界就是智能体的提示词，因此在这种轮次运行时入队的**引导**消息会中断该提示词，轮次会带着排队内容重新开始 - 这正是"有等待队列时按 Stop"手工完成的事，只是替你做好了。智能体会保留自己的 ACP 会话，因此它会从已经完成的工作继续，它已经写下的答案会留在对话记录中。**轮次之后**消息在那里不改变任何东西：智能体完成，消息在该轮自己的边界被读取。当队列中存在要求等待的消息时，不会有任何东西被中断。

## 图片

输入框附件会随其文本一起进入队列，仅含图片的消息也是有效的。只有当会话的模型能读取图片（`multimodal: true`）时，图片才会到达模型，这与普通提示词遵循的规则一致：对于纯文本模型，服务器会丢弃排队消息中的图片并保留其文本。只接受随请求本身携带的图片，即 base64 的 `data:image/...` URI；其他任何形式都会被拒绝。当智能体读取该消息时，Coddy 会把图片随会话的资产一起保存、发送给模型，并在对话记录中的用户消息上显示它。

在等待期间，图片留在服务器上。发送给每个客户端的列表只标明每张图片（名称、类型和大小），从不携带其字节：队列的每次变更都会发给该会话的每个客户端，否则几张截图就会随每次变更一起传输。字节只会回到撤回该消息的客户端，由它放入自己的草稿。

排队文本开头的设置命令（`/model x`、`/permissions bypass`）会立即生效，只有其余部分等待；若文本只有命令，其图片仍会排队（[会话设置](session-settings.md#发送命令时会发生什么)）。

## 队列的生命周期

队列存在于 `coddy serve` 进程的内存中：

- 它在一轮运行期间接受消息，而在没有工作的会话上拒绝消息：此时该界面会把那段文本作为普通提示词发送；
- 由完全取消保留的轮次之后消息，以及被已接受的续跑预留后又停止的未读批次，会在空闲会话上保持可见，直到它们运行或被移除；
- 进程重启后不保留任何内容；
- 最多同时有 **20** 条消息等待。队列是输入框的一项便利功能，不是批处理运行器。

**子（子智能体）会话**不接受任何消息。它唯一的一轮是其父级写下的任务，出于同样原因，它在其他一切地方都是只读的。

## 在浏览器中

![浏览器输入框上方的引导消息与轮次之后消息](../../assets/message-queue/message-queue-modes-dark-1280.png)

*每条等待中的消息都会显示其模式，以及一个带有图片数量的回形针。*

![窄屏幕上的等待消息](../../assets/message-queue/message-queue-modes-dark-390.png)

*在 390 px 宽度下，模式与图片数量仍然可见。*

智能体工作期间输入框保持可用。若输入框中有草稿，其右侧的圆形控件会以 Enter 模式将其入队，而不是停止该轮；若输入框为空，它就是 **Stop generation**，会请求上文所述的队列续跑，或在续跑不可用时执行完全取消。排队的消息按智能体将要读取的顺序堆叠在输入框上方。点击消息的模式可切换它；其角上的叉号可撤回它，并把它的文本和图片放入草稿，置于此后输入的任何内容之前，因此撤回消息就是编辑它的方式。若智能体在按下叉号之前已经读取了该消息，它已经在对话中，什么也不会返回。

浏览器在打开和重连时会检查所选会话的活动与队列，但在自己的提示词请求等待接纳期间会跳过这两项读取。即使该标签页丢失了流读取器，或该会话不在当前 History 页面中，正在运行的轮次仍可使用 Stop 和入队。Stop 会发送取消请求并立即关闭该标签页自己的读取器，因此当其他标签页占满一个浏览器对单一主机允许的其余连接时，该请求绝不会等待那个读取器所占用的连接；请求失败会显示错误，标签页会重新加入正在运行的轮次，控件仍可用于再次尝试。在 `queueContinued: true` 下，浏览器通过输入框中继重新挂接到同一轮次代际，而无需等待另一次 `turn_started`。它绝不会排空队列，也不会在本地重新提交其消息。没有该标志时，服务器在确认取消后可能仍需要时间释放该轮次。现有的代际防护仍然有效；当一个旧的轮次结束事件与挂起或已接纳的提示词重叠时，需要一次新的活动读取，浏览器才会宣布空闲。

## 共享会话拥有共享队列

会话并不归打开它的标签页所有。两个浏览器、手机上的第三个窗口，以及通过 `--remote` 连接的某个控制台，可以同时查看同一个会话，而队列属于会话而不是其中任何一个：任何人入队的内容都会对所有人出现，某个人撤回或切换的消息会对所有人改变。

无论是否有客户端正在读取运行中轮次的流，这一点都成立。每次变更都沿两条路径传播：

- **该轮次自己的流**，因此驱动该轮次的客户端以及任何 tee 到它上面的客户端（`GET /coddy/sessions/{id}/composer-stream`）会立即获得；
- **`GET /coddy/events`**，即每个浏览器都保持打开的全服务器范围流（其各标签页共享一个连接），控制台在 `--remote` 下订阅它，它携带带有会话 id、整个队列及其版本的 `event: message_queue`。

无论哪个请求造成了该变更，其响应都携带相同的列表和版本，因此它是同一事实的第三次投递，而不是另一份真相。

这些是不同的连接，因此投递可能以任意顺序到达。每次投递都携带一个**版本**，用于计数该会话队列的变更；普通投递保留所见最高版本并丢弃更旧的版本。对于事件和 HTTP 响应，服务器都在同一把锁下读取列表和版本。计数器是进程范围而非会话范围的，因此重建实时状态不会在该进程内复用更早的版本。对于服务器重启后的浏览器恢复，只有在读取期间没有队列投递穿插时，一次新的队列 GET 才可以确立更低的版本，包括 `0`。这种恢复会推进本地纪元，因此浏览器会忽略在更早纪元中捕获的变更响应以及自身/中继流的队列帧。重放的轮次开始事件本身不会清除客户端的版本或等待中的消息。

## 在控制台中

![带有引导消息与轮次之后消息的控制台队列](../../assets/message-queue/message-queue-console-modes-dark.png)

*控制台为等待中的消息编号，并在编辑器上方显示各自的模式。*

![控制台询问 Enter 应使用哪种模式](../../assets/message-queue/message-queue-console-choice-dark.png)

*在一轮进行中写下的第一条消息会在状态行上询问：1 引导，2 轮次之后，Esc 把草稿放回。*

在一轮运行时提交会以 Enter 模式把提示词入队，而 **Tab** 以另一种模式入队。第一次时，控制台会在状态行上询问 Enter 模式（**1** 引导，**2** 轮次之后，**Esc** 把草稿放回），把答案保存到 `agent.queue_mode` 并将消息入队；用 Tab 发送的消息仍走另一种模式。等待中的内容会显示在输入区正上方，按读取顺序编号：

```
queued messages (2) · /queue to manage
1. [steer] check the Windows path too
2. [after_turn] and then update the changelog
```

`/queue` 列出它们，`/queue mode <n> steer|after_turn` 切换其中一条，`/queue drop <n>` 撤回一条并把其文本放入输入区，`/queue clear` 清空队列。按 **escape** 取消该轮：它未读的引导消息随之消失，而轮次之后的消息继续排队。对远程服务器（`--remote`）同样有效：控制台会调用下面的队列路由，并订阅服务器的事件流，因此别人在浏览器中排队的后续消息也会出现在控制台输入区上方。

在远程控制台中，由其他客户端启动的轮次也接受排队输入和 Escape 取消。控制台会将该服务器活动与自己的提示词请求分开跟踪。服务器重启后，只有在读取期间没有队列更新穿插时，最新的新鲜队列快照才能恢复更低的版本（包括零）；恢复前延迟到达的回复和通知无法恢复旧行。恢复不要求轮次空闲。读取失败或被穿插的快照会重新读取（最多三次尝试，间隔很短）；更新的刷新或客户端关闭会停止旧的恢复。队列读取有与活动读取分开的超时预算。这种控件支持不会让控制台挂接到其他客户端的实时对话记录，也不会共享其权限和问答对话框。

## 通过 HTTP

| 路由 | 作用 |
|---|---|
| `GET /coddy/sessions/{id}/queue` | 等待中的内容：`id`、`text`、`mode`、`imageParts`（每张图片的 `name`、`mimeType` 和 `sizeBytes`，绝不包含其字节）以及每行的 `createdAt`，还有队列 `version`。 |
| `POST /coddy/sessions/{id}/queue` | 将 `{"text": "...", "mode": "steer\|after_turn", "inline_files": [{"name": "shot.png", "data_url": "data:image/png;base64,..."}]}` 入队。`mode` 默认 `steer`；随带图片时 `text` 可以为空。**201**，返回存储的消息和整个队列。 |
| `PATCH /coddy/sessions/{id}/queue/{message_id}` | 用 `{"mode": "steer"}` 或 `{"mode": "after_turn"}` 切换一条等待中的消息；返回整个队列。 |
| `DELETE /coddy/sessions/{id}/queue/{message_id}` | 撤回一条。响应携带队列的其余部分，并作为 `message`，携带撤回的消息及其完整图片置于 `inline_files` 下，形式与 POST 接受的一致。 |
| `DELETE /coddy/sessions/{id}/queue` | 丢弃所有等待中的内容。 |

没有轮次运行的会话会以 **409** 和代码 `no_active_turn` 拒绝 POST；满队列以 `queue_full` 返回 **409**；子会话以 `subagent_read_only` 返回 **409**。不是 base64 `data:image/...` URI 的 `inline_files` 条目会以 `invalid_request` 返回 **400**，而无法读取图片的模型会把它们排除在存储的消息之外。对智能体已先行读取的消息执行 PATCH 或 DELETE 会以 `not_found` 返回 **404**：输掉这场竞争是正常的，消息已经在对话中了。`--once` 或 `--count=N` 命令后跟文本会以 `turn_scoped_follow_up` 返回 **409**：排队消息仍可切换模式或被撤回，因此该命令没有自己可等待的轮次（[会话设置](session-settings.md#发送命令时会发生什么)）。如果一轮在按键与队列接纳之间结束，浏览器和远程控制台会把提交的文本恢复为草稿，而不是自动启动另一个提示词。

每次变更都会作为 `event: message_queue` 发布，携带完整列表及其版本，在轮次流和 `GET /coddy/events` 上都是如此。智能体读取的引导消息，以及轮次之后消息在其运行开始时，都会作为 `event: user_message` 到达轮次流，位置是它们进入对话的地方。完整形式：[HTTP API](../reference/http-api.md)。现有的取消路由接受可选的 JSON 请求体 `{"continue_queue":true}`。空请求体（EOF）、`null`、`{}` 或 `{"continue_queue":false}` 保持默认的完全取消。无效 JSON 或非布尔的 `continue_queue` 返回 **400**。

## 它不是什么

- **不是调度器。** 等待中的消息不会在重启后存活。完全取消会保留轮次之后消息，以及已被接受的续跑所预留的任何未读批次；它不会自动启动它们。
- **不是第二次接纳。** 轮次之后的运行和被接受的 Stop 续跑仍留在已接纳的轮次内，每次运行使用一把轮次锁和新的 `agent.max_turns` 预算。完全取消会停止这条链。
- **不是跨进程的队列存储。** 共享控制要求客户端属于同一个 `coddy serve` 进程。共享会话目录的独立本地控制台或 ACP 进程不会共享其内存中的队列。跨进程取消仍使用 bundle 的取消标记。
- **不共享问题或权限。** 闸门归属不变：权限或问题提示仍留在启动该轮次的界面上。
