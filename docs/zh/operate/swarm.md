# 集群：中继、节点，以及一份包含一切内容的列表

https://github.com/user-attachments/assets/2a26f40a-97dd-46ef-b554-80e53602ed44

*一段三分钟的录屏，基于 1.3.0：控制台中有两个中继和三个节点，随后把该中继作为一台笔记本电脑 Web 界面的远程环境，在图形布局中查看地图，跨两个中继回答一次权限请求，以及查看位于两个中继之后的某个节点的文件与编辑窗口。该文件位于仓库中：[swarm.mp4](../../assets/video/swarm.mp4)。*

**集群**是一组通过一个或多个**中继**访问的 coddy 节点。中继是无状态的会合点：节点注册到其中，它把请求转送给这些节点，并把它们的会话列表合并成一份。它自身不存储任何内容，因此它报告的内容始终只是节点告诉它的实时视图。

使用 `-tags swarm` 构建，它属于随发布提供的内容（**Makefile** 中的 `FULL_TAGS`），因此发布二进制、Docker 镜像、Linux 软件包和 Homebrew formula 都包含该中继。使用 `make build TAGS="http ui scheduler memory cli gateway swarm metrics browser"` 自行构建。

中继不是它自己的命令：当 `swarm.enable` 为 true 时，`coddy serve` 会运行它，与配置启用的其他内容并列。未使用该标签构建的二进制会在启动时拒绝 `swarm.enable` 并指出该标签；智能体侧的加入钩子是一个存根，不启动任何 goroutine，也不打开任何连接，除此之外该二进制行为与该功能存在之前完全一致。

## 为什么

在多台机器上运行 `coddy serve` 已经可行，且 `--remote` 已经能驱动其中一台。它没有提供的是一个查看一切的地方，或者在你要的机器位于你无法拨号到达的地方时进入它的方式。

中继同时解决这两点。它知道加入它的每个节点，因此连接到它的客户端会一次性看到这些节点的全部会话，并按所有者标注。而且完全没有入站路由的节点也可以加入，因为该节点会自行打开连接。

## 它的形态

```
    client ──▶ relay "outer" ──┬──▶ relay "middle" ──▶ agent8
                               │                   └──▶ relay3 ──▶ agent7
                               └──▶ relay3 (shortcut) ──────────┘
```

那张图里有三点值得注意。

从父节点的视角看，中继就是一个节点。`middle` 加入 `outer` 的方式，与 `agent8` 加入 `middle` 完全相同，这就是链式连接所需的全部 - 不需要第二种机制，也没有任何一跳需要知道链有多深。

`relay3` 可以通过两条路径到达。这是一个环，且这是允许的：集群按身份对其去重，并选择较短的路由。

`agent7` 从未打开端口。它拨号到 `relay3`，并被沿着同一连接反向驱动。

## 运行一个中继

```yaml
# a relay
swarm:
  enable: true
```

```bash
coddy serve --swarm-auth-token "$CLIENT_TOKEN" --swarm-pairing-token "$PAIRING_TOKEN"
```

一个不应做其他事的中继会添加 `--http=false`。一个同时也是普通智能体的中继会保留 API 开启，于是同时提供两者：它自己的会话位于 `httpserver.port`，整个节点群位于 `swarm.port`。这样的进程会作为中继，向 `swarm.join` 中的每个中继注册一次：该中继代表该进程发言，因此其父级可以到达它后面的节点，而它自己的会话仍留在 `httpserver.port`。给它的加入条目使用该中继的地址，即 `swarm.port` 上的地址，作为 `advertise_url`。

节点通过在自己的配置中列出中继来加入：

```yaml
swarm:
  join:
    - url: "https://relay.example"
      name: "nas02"                        # becomes a URL path segment
      pairing_token: "${CODDY_SWARM_PAIRING_TOKEN}"
      advertise_url: "https://nas02:12345" # omit this to dial out instead
      token: "${NODE_OWN_TOKEN}"           # what the relay presents when it proxies
```

`swarm.join` 会被每个 `coddy serve` 进程遵循，无论它是否运行自己的中继。这种对称性正是中继链式连接的方式。

尽可能显式设置 `swarm.join[].token`；建议使用专用于父中继的凭据，显式值始终优先。当中继省略该令牌时，它会回退到配置的 `swarm.auth_token`，以便父级可以通过其挂载点进入子中继。智能体不会获得此回退：没有加入令牌的智能体会在没有节点凭据的情况下注册。

名称是可选的。没有 `name` 的加入条目会使用其运行所在机器的主机名（点会变成短横线，因为名称是路径段），而没有 `swarm.name` 的中继也会以其主机名出现，出现在 `/swarm/info` 中、地图上以及其会话的路由中。当两台机器共享主机名，或主机名无法说明有用信息时，请设置名称。

## 两种传输方式

**直接** - 中继拨号到节点的 `advertise_url`。当中继可以到达节点时使用它。

**隧道** - 省略 `advertise_url`。节点拨号到中继，中继接管该连接，从那时起中继沿该连接发送请求，而节点回应它们。当网络不接受任何入站连接时，这是唯一的进入方式，移动网络上的手机也属于这种情况（[作为集群节点的 Android 手机](../tutorials/swarm-android-nodes.md)）。

隧道是在一条最初作为普通 HTTP 请求开始的连接上使用 prior-knowledge HTTP/2，因此没有定制的帧协议，也没有新的依赖。传输层之上的一切都组合普通 HTTP，且永远不会知道正在使用哪一种传输。

它确实需要一条**端到端原始连接**。会对请求重新分帧的中间层 - 例如第 7 层代理，或位于中继前面的仅支持 HTTP/2 的终止器 - 不会留下可供接管的内容，握手会失败并给出明确说明这一点的错误。直接传输方式不受影响。

## 访问节点

每个节点都挂载在中继之下：

```
GET https://relay.example/swarm/nodes/nas02/coddy/sessions
```

因为那是一个带路径的普通基础 URL，**今天的客户端无需改动即可工作**：

```bash
coddy --remote https://relay.example/swarm/nodes/nas02 --remote-token "$CLIENT_TOKEN"
coddy acp --remote https://relay.example/swarm/nodes/nas02 --remote-token "$CLIENT_TOKEN"
```

链式连接通过写出路径来组合：

```
/swarm/nodes/middle/swarm/nodes/relay3/swarm/nodes/agent7/v1/models
```

每一跳都会剥离自己的前缀并转发其余部分。

### 挂载点会承载什么、不会承载什么

它会承载 `/v1/*`、`/coddy/*`、只读的集群路由，以及更多的 `/swarm/nodes/*` 跳。那是一个**前缀**允许列表，而不是路由列表，因此节点新增的路由在发布当天就能工作。

它会拒绝 `POST /swarm/register`、`POST /swarm/tunnel` 和 `DELETE /swarm/nodes/{node}` - 最后一项是按方法拒绝，因为读取子中继的节点列表是普通操作，而从中驱逐节点则不是。代理会代表调用方对节点进行认证，因此通过挂载点可访问的任何内容都是中继为其授权的；成员资格决策不属于此列。

通过中继工作的浏览器只会听到中继的 CORS 应答（`swarm.cors`），不会听到别的：节点自身应答中的 `Access-Control-*` 头会留在挂载点之后。对于浏览器也会直接访问的节点，如果开启了 `httpserver.cors` 并让其头通过，这些头会与中继的头并列 - 浏览器会拒绝一个两次声明允许来源的响应。同样的规则会阻止节点的策略去打开一个自身 CORS 已关闭的中继。由于中继的应答是唯一应答，它会携带 Web 界面的文件窗口从另一个来源所需的内容：方法中的 `HEAD`，请求头中的 `Range` 和 `If-None-Match`，以及向页面暴露的 `ETag`、`Content-Range`、`Accept-Ranges` 和 `Content-Disposition`。

[Coddy for Browser](../features/browser.md) 扩展的 WebSocket（`/browser/v1/`）不会被承载：浏览器会在其自己的机器上连接到节点。另一个节点的聊天会通过该节点挂载点的 `/coddy/browser/v1` 到达该浏览器，前缀列表会像对待任何其他路由一样承载它（[其他 Coddy 进程的聊天](../features/browser.md#其他-coddy-进程的聊天)）。

手写路径会受到与扇出相同的跳数预算限制，因此客户端不能通过一个接一个地写出跳来无限遍历一个环。

## 聚合列表

```
GET /swarm/sessions?q=&node=&limit=&include_activity=
```

每个节点都会被并行询问，并受截止时间限制，答案会按最新优先合并。子中继会被要求提供它自己的聚合结果，而不是它的节点列表，因此合并会沿链递归，而每个中继仍然只与其直接子级通信。

每一行都同时带有**身份**和**路由**：

- `agent_uuid` + `id` - 拥有该会话的智能体，以及该智能体用来识别它的 id。该对值在重命名、故障转移或中继重启后仍然存在。
- `node_path` - 此中继当前可以如何到达它。在环中可能有多个，报告的是最短的那个。在两个同样短的路由中，首个不同跳按名称排序更靠前的路由获胜，比较是逐跳进行，而不是把整条路径连接起来比较。拓扑为节点选择路由时也是如此，因此一行不会在两次请求之间改变路由。

会话 id 是按节点选择的，且**确实会**冲突，因此任何以裸 id 为键的内容都不安全。

缓慢或消失的节点会成为 `warnings` 中结果旁边的条目，而不是代替结果的错误：一台不可达的机器不应让整个节点群列表变为空白。

**搜索**覆盖工作和机器。匹配节点名称或地址的词会返回该节点持有的所有内容；否则该词会被下推到每个节点，由节点将其与会话标题、首条用户消息和工作目录进行匹配。

## 环与路由

`GET /swarm/topology` 返回节点、节点之间的边以及每个节点的一条路由。

路由来自广度优先遍历，它按跳数递增访问 - 因此找到的第一条路由就是最短路由，而已见过的节点不会再次展开，这也是环会终止而不是空转的原因。平局按字典序打破，因此向同一中继提问的两个客户端会得到相同的路由。路由从不重复某一跳，因此它不会在途中绕圈。

`alternates` 是遍历看到的、到达**该节点**的其他边，长度不限 - 当短跳失效时，客户端会在那里故障转移。它们不是从进入某个祖先的另一条路径继承来的路由：经过合并点之后，只会向前携带穿过该点的最短路径，因此菱形结构之后的节点只有一条路由，而不是两条。枚举每条 k 最短路径会让列表充满推测；故障转移列表保持正确且简短更有用。

对于每个**请求**，中继会把自身 id 追加到内部头中，并拒绝已经携带该 id 的请求，因此遍历不会永远绕下去。对于手写的挂载路径，深度也以同样方式设限。

在遍历中闭合回自身的分支会返回 `looped: true` 且不贡献任何内容，而不是发出警告。仅仅**过长**的链则是另一种答案：外面确实有东西但无法到达，因此那种情况会警告。在环中，这是分支的正常终点，而在健康集群中每个请求都发出警告，正是让运维人员学会忽略警告的方式。真正值得警告的是一个中继仍然知道但无法到达的节点 - 包括已过期的租约，否则它会静默消失，并让“这台机器宕机”看起来与“这台机器没有工作”一模一样。

连接就是普通的环境流程：侧栏底部的环境菜单，**"连接到…"**，中继的地址及其客户端令牌 - 或者 `httpserver.remotes` 中一个指定该中继的条目，并在你将其保存在那里时带上其 `token`（[远程模式](remote.md#令牌)）。从另一台机器提供的页面，例如一台笔记本电脑的 `coddy serve`，还需要中继的 `swarm.cors` 来接纳其来源：精确地写在 `allowed_origins` 中，或者 - 对于回环地址上的页面，无论笔记本电脑的 `coddy serve` 占用了哪个端口 - 通过 `allow_loopback: true`；当阻碍就在于此的时候，环境菜单会在中继那一行说明这一点，并在接受令牌后列出该中继的智能体，因此节点也距离菜单只有一次点击。由于环境会以中继身份应答，侧栏中会出现一个**"集群"**条目 - 在普通智能体上则完全不会出现。

集群界面会显示拓扑和一个会发往中继的搜索框。它会在一个与文档阅读器一样宽的停靠区中打开，地图会填满其中。

**选择布局，然后探索地图。** 地图初始为**"树状布局"**，即显示跳数层级的根视图。**"图形布局"**是一种确定性的有根图，用于检查环和交叉链接：中继是其根，或者当地图显示启动连接的机器时，本地计算机是根。它按最短路由深度向下展开：每个中继的节点在其下方沿一条弧线扇形展开，链式中继挂得更深，其链接是直线。该选择只属于此浏览器，位于 localStorage 键 `coddy_swarm_layout` 下；它不会改变中继配置或另一个浏览器。保存的旧版 `star` 值会迁移到图形布局；如果该键缺失、不可用或无效，树状布局仍是默认值。

地图有“树状布局”和“图形布局”选择器，以及**"缩小"**、**"适应图形"**和**"放大"**控件。滚轮缩放以指针为中心；即使图形已适应，拖动也可在两个轴向上平移；两指捏合可缩放；拖动或捏合不会激活节点。地图获得焦点时，**`+`** 或 **`=`** 放大，**`-`** 缩小，**`0`** 适应整个图形。在堆叠外壳上，地图控件是 40px 的触控目标。适应会重置相机，切换中继或布局也会重置；普通的五秒拓扑轮询不会丢弃手动平移或缩放，不过它会让相机保持在变化后的图形边界内。

![带有地图控件的图形布局](../../assets/swarm/map-graph-canvas-dark-1280.png)

*图形布局：中继的节点在其下方扇形展开，相机控件位于地图上方。*

正在使用的路由是一条强调路径。它经过的每个中继都会被描边，其中应用当前正在驱动的中继描边更强；备用路由则明显保持次要地位。这样一来，中转中继可以被读作连接的一部分，而不会被暗示为所选目标。

**中继的主屏幕就是集群。** 对于智能体的 API，中继只提供其自己的设置（`/coddy/config*`） - 没有会话、没有工作区、没有模型、没有文档 - 因此输入框没有可发送的对象，历史抽屉也没有可列出的内容。因此当指向中继时，应用会去掉聊天界面，隐藏侧栏中的历史与调度器，改为显示地图。环境菜单仍在它一贯所在的位置，即侧栏底部，因此即使地图报告错误，包括中继需要令牌，运维人员也可以切换环境或提供所需凭据。进入一个节点后，这一切都会回来，因为节点确实拥有那些内容。

**在节点上工作。** 点击地图上的节点，应用会指向该节点的挂载点，同时地图会保持打开并覆盖在其上，直到你选择在那里做什么。从那里开始，所有已存在的界面都会驱动它 - 历史抽屉列出该节点的会话，输入框显示其工作目录和模型目录，设置会编辑该节点的配置 - 中继在中间，而没有任何界面知道它的存在。节点上的长对话也会在那里逐页读取：每次读取都会在查询字符串中指明其页面，挂载点会将其原样带到节点，通过隧道时也是如此（[长会话](../surfaces/web-ui.md#长会话)）。文档阅读器是唯一留在页面自身服务器上的界面：页面是本地二进制所携带的那些页面。

![在某个节点上方打开的集群地图，连接从本地机器开始](../../assets/swarm/map-over-node-dark-1280.png)

*在某个节点上方打开的地图：页面运行所在的机器位于顶部，通往应用所在节点的路由被绘制为一条路径*

**从地图观察。** 每个节点都会说明它正在做什么，信息来自搜索所使用的同一份聚合会话列表：它持有多少会话、有多少轮次正在进行，以及那里是否有内容正在等待权限提示。在几台机器上开始工作，回到地图，它会说明哪些已完成，哪些正在向你提问。点击正在提问的那个，应用会切换到它，同时地图仍然打开；其历史会显示等待你的那个会话。

**返回与切换。** 当你位于某个节点内部时，集群条目仍留在侧栏中，因为你经过的中继会被记住。它会在节点上方打开该中继的地图，而不会离开该节点：地图会使用相同的客户端令牌直接从该中继读取，而节点的历史、调度器和聊天保持原样，因此不会重新加载。在那张地图上，你所在的节点带有一个环，就像你在中继上时中继卡片带有环一样，通往它的路由被绘制为一条连通的路径；另一个节点只有一次点击之遥，而点击你所在的节点则不会有任何操作。在节点之间，或在节点与其中继之间切换，不会重新加载页面。在中继上方，地图会把页面运行所在的机器绘制为连接的起点，并以它的主机名命名：点击它会回到本地。点击中继会连接到中继自身，而位于其下的链式中继会通过这个中继到达并打开自己的地图。在中继自身上，中继不是按钮：没有什么可连接的。

**SPA 来自哪里。** 使用 `-tags "swarm ui"` 构建时，中继会在自己的地址上提供控制台，因此中继就是你在浏览器中打开的东西。它与节点提供的打包资源相同，并把中继视为又一个环境：在需要令牌的中继上以同源方式打开时，它会说明这一点并要求提供令牌，而不是报告一个空集群。未使用 `ui` 标签构建时，中继的根路径会解释如何重新构建，而控制台仍可从任何节点打开并指向该中继。

## 设置位于何处

| 内容 | 位置 |
|---|---|
| 此进程是否进行中继 | `swarm.enable` 在 `config.yaml` 中，或 `--swarm` / `--swarm=false` |
| 中继自身的部署：绑定地址、客户端与配对令牌、TLS、静态上游 | `swarm:` 在 `config.yaml` 中，或 `--swarm-*` 标志 |
| 此进程加入哪些中继 | `swarm.join` 在 `config.yaml` 中 - 无论此进程是否进行中继都会遵守 |
| 界面环境菜单中提供的中继 | 页面服务器的 `httpserver.remotes`：名称、URL，以及可选的客户端令牌（`token`，最好作为 `${ENV}` 引用） |
| 可在别处提供、并可调用中继的页面 | `swarm.cors`（`enable`，针对任意回环端口上笔记本电脑 Web 界面的 `allow_loopback`，`allowed_origins`） |
| 来自文件的凭据 | `CODDY_SWARM_TOKEN`、`CODDY_SWARM_PAIRING_TOKEN`、`--swarm-auth-token`、`--swarm-pairing-token` |

**中继自身的设置。** 在中继上打开时（其地图是页面的主页），设置抽屉会编辑中继的部署及其日志：**"集群中继"**标签页（名称、监听地址、客户端与配对令牌、CORS、TLS、租约与扇出超时、上游、加入）以及**"日志记录器"**。没有会话标签页，因为中继不持有会话。路由是智能体自己的 - `GET /coddy/config/schema`、`GET /coddy/config`、`POST /coddy/config/validate`、`PUT
/coddy/config` - 由中继在其客户端令牌之后提供，且它们只携带这两个章节：宿主的其余配置 - 模型提供商的密钥、HTTP 服务器 - 既不会通过中继显示，也不会通过中继写入，而指定另一章节的保存会被拒绝。

![中继上的设置抽屉](../../assets/swarm/relay-settings-dark-1280.png)

*中继的设置：其部署，凭据为只写*

那里的每个凭据都是只写的，正如配置读取所提供的那样：令牌字段显示是否已设置，空字段会保留它，值会替换它。配对令牌是一个整体替换的列表。保存会写入中继的 `config.yaml`，并保留其注释和拼写，然后中继会基于它重建：节点会在数秒内重新注册并重新打开它们的隧道，而通过中继进行中的流会被切断并由客户端恢复。新的监听地址需要重启，而调度器或 systemd 下的中继会自行获得重启。在仅作为中继启动的进程文件中开启 HTTP 服务器、网关或调度器也是如此：它没有打开会话存储，而那些界面会运行智能体轮次。新的客户端令牌会让每个客户端退出登录，包括你正在保存的页面：请在环境菜单中输入新的令牌。**"日志记录器"**标签页像其余部分一样保存，中继会在下次启动时读取它，就像智能体处理自己的日志记录器设置一样。对文件的编辑也会以同样方式被拾取，无需重启。

通过另一个中继更改中继的设置会被拒绝：位于此中继之下的链式中继会像任何节点一样通过挂载点到达，但它的令牌及其注册规则决定谁加入它，而父中继的客户端不是它的运维人员。通过挂载点读取它们则可行。

## 安全性

三种凭据，三项职责：

| 凭据 | 谁持有 | 它授权什么 |
|---|---|---|
| `swarm.auth_token` | 客户端 | 使用此中继 |
| `swarm.pairing_tokens` | 节点 | 加入此中继 |
| 每节点 `token` | 中继 | 充当该节点 |

**中继是一扇通往整个节点群的门。** 它持有每个节点的凭据，因此任何持有其客户端令牌的人都能控制它到达的每个节点，并会传递地穿过每一跳 - 其会话、其工具及其设置，包括节点的 `GET /coddy/config` 交回的机密（提供商密钥、远程令牌）。这里是在陈述这一点，而不是缓解它：此版本中没有按节点划分的客户端 ACL。请为每个节点提供专为其中继铸造的凭据，而不是你自己的凭据，在前面部署 TLS，并保守配对令牌的秘密。

在没有客户端令牌的情况下绑定到非回环地址会**拒绝启动**（`swarm.allow_insecure` 会覆盖此行为）。在回环上，会为本次运行生成一个令牌，而不是留空，因为开放的中继会把其权限借给每个本地进程。生成的值会写入 `${CODDY_HOME}/swarm-token`，仅所有者可读，并在中继停止时移除；当它是终端时也会写入 stderr。它永远不会写入日志，而后台或 systemd 下的中继，其 stderr 是日志，因此不会打印它。如果文件和终端都没有收到该令牌，中继会拒绝启动。

节点的名称由中继铸造的**每租约密钥**证明，而不是由共享配对令牌证明：节点群凭据绝不能允许一个节点声明另一个节点的名称、重定向其流量或读取发给它的提示词。该密钥存储于 coddy home 下，因此重启后可以立即收回同一名称。中继会在 `${CODDY_HOME}/swarm-names.json` 中保留每个名称密钥的摘要，因此即使租约消失，名称仍保持绑定 - 无论是在重启或保存设置重建中继之后，还是在节点离线超过宽限期之后 - 只有持有该密钥的节点才能取回它。`DELETE /swarm/nodes/{node}` 是管理性接管路径，可释放名称，无论是否有活动租约，这也是丢失密钥的节点找回名称的方式；`swarm.upstreams` 中具有相同名称的条目会接管它。如果绑定文件不可读或格式错误，中继会拒绝启动。注册或删除只有在当前绑定快照持久化后才会被确认。存储失败会返回 HTTP `500`。在绑定文件被替换之前的失败会让名称保持不变；替换之后，目录同步失败可能使更改已应用，尽管其持久性尚未确认。

通告的 URL 是一个 **SSRF 边界**。仅允许 `http(s)`，且不带凭据、查询或片段；随后会解析主机并检查每个地址。链路本地、组播、未指定和云元数据地址会被直接拒绝。仅当中继自身绑定到回环（开发场景）时才允许回环，且仅当 `swarm.allow_private_upstreams` 指定主机时才允许私有范围 - 这也会将这些名称加入允许列表。通过检查的地址会被**固定**，中继会精确拨号这些地址，因为拨号时重新解析会重新打开检查所关闭的窗口。

代理会**替换**调用方的 `Authorization`，而不是转发它，会剥离 Cookie、逐跳头和转发头，在跳之前移除 SSE 查询令牌，并且从不跟随重定向。路径段是在**解码之后**判定的：`%2e%2e` 会通过任何对转义形式的检查，并在某处解码它的瞬间变成 `..`，这正是针对节点 API 的请求可能爬回中继自身路由的方式。

有一类请求在没有客户端令牌的情况下被承载：对节点 `/coddy/sessions/{id}/workspace/raw` 的 `GET` 或 `HEAD`，带有 `access_token` 且没有 `Authorization` 头。这就是 Web 界面的文件窗口播放视频或音频文件并下载文件的方式：媒体元素无法发送头，因此节点会为某个会话的某个文件签署能力，有效期一小时，而浏览器会把它放进地址中。中继无法检查该签名，也不为其背书：请求会带着查询中的能力到达节点，且不带中继自己的凭据，由节点接受或拒绝它。带有两个 `access_token` 值的请求不属于该例外，而且中继的客户端令牌绝不会以这种方式在任何路由上被携带。没有客户端令牌时，此类请求从中继自身那里除了门禁的普通 `401` 之外什么也得不到，用于中继会拒绝的内容（未知或不可达节点、它不承载的路径）；否则只有节点会回答它。不要求客户端令牌的中继也会以同样方式转交这样的请求，不带自己的凭据，因此链中位于它上方的带门禁中继无法通过它被绕过。

[画布](../features/canvas.md) 的帧是第二类此类请求：对节点 `/coddy/canvas/<capability>/<path>` 的 `GET` 或 `HEAD`，没有 `Authorization` 头，通过一个挂载点或一串挂载点。帧是一个 iframe，其页面在不透明来源中运行，并从其地址加载自己的脚本和文件，因此能力位于路径中：节点为某个会话的某个帧签署了它，只有节点会检查它。中继会在不带自己凭据的情况下承载该请求，用自己的 `Access-Control-Allow-Origin: *` 回答其 CORS（包括预检），并传递节点的 `Content-Security-Policy`，这正是让页面保持在其沙箱中的原因。对于所有其他 `Origin` 为 `null` 的请求 - 沙箱页面发送的内容 - 中继都会以 `403` 拒绝，无论它携带什么凭据，因此画布上的页面也无法通过中继访问节点 API。

凭据在配置保存时按**目的地**保留，而不是按标签保留：重命名条目会保留其令牌，将其指向新地址则不会。

中继自身的设置（上文）会用客户端令牌编辑它，而该令牌已经控制它到达的每个节点；它们不会增加令牌原本没有的权力，也无法通过父中继的挂载点访问。

## 加密与代理

中继通常位于不同网络中。

```yaml
swarm:
  tls:
    cert_file: "/etc/coddy/relay.crt"
    key_file: "/etc/coddy/relay.key"
  join:
    - url: "https://parent.example"
      dial:
        proxy: "socks5://127.0.0.1:1080"   # http, https, socks5, socks5h
        ca_file: "/etc/coddy/internal-ca.pem"
```

两个文件都要提供，或都不提供；最低 TLS 1.2；证书是启动状态，因此轮换它们需要重启。`insecure_skip_verify` 用于实验室环境，并且每次使用时都会记录日志。

通过代理向 TLS 中继打开隧道可以组合：拨号到代理，向中继发送 `CONNECT`，包裹 TLS，升级，反转角色。上方的 HTTP/2 层对此一无所知。

## 有意缺失的内容

- **没有持久化。** 注册表位于内存中；节点通过签到使它再次为真。重启后，`/swarm/info` 会报告 `registry_warming`，以便客户端区分“刚刚启动”和“这里什么都没有”。
- **没有跨节点分页。** 每个节点返回第一页，合并时会截断；某个节点的深层历史会通过其挂载点使用该节点自己的分页。
- **一条隧道就是一个连接。** 重新连接会结束旧连接上正在运行的流，而批量响应会与活动轮次共享流控。这两点都是每个节点单条 HTTP/2 连接的固有属性，且不会被规避。
- **每个端点一个中继进程。** 负载均衡器后面的两个副本会分裂注册表和隧道。
- **没有按节点划分的客户端授权。** 参见上文的爆炸半径。
